# Proxy 代理模式（Python）

## 意图

为其他对象提供一个替身或占位符，以控制对这个对象的访问。本例展示最常见的
**虚拟代理**（Virtual Proxy）用法：将开销很大的对象创建过程推迟到真正需要时才执行。

## 适用场景

- 远程代理：为远程对象提供本地代表（如 RPC 客户端桩）
- **虚拟代理**：延迟创建开销很大的对象，直到真正被使用（本例：图片懒加载）
- 保护代理：控制对原始对象的访问权限
- 缓存代理：对结果进行缓存复用，避免重复的昂贵操作

## 实现方式

`Image` 是抽象主题；`RealImage` 是真实主题，构造时立即从"磁盘"加载（模拟耗时操作）；
`ImageProxy` 也实现 `Image` 接口，但构造时只记录文件名，直到第一次调用 `display()` 才
真正创建 `RealImage` 并缓存：

```python
class ImageProxy(Image):
    """虚拟代理：延迟创建 RealImage，直到第一次真正需要显示时才加载"""

    def __init__(self, filename: str) -> None:
        self._filename = filename
        self._real_image: RealImage | None = None  # 尚未加载

    def display(self) -> None:
        if self._real_image is None:
            self._real_image = RealImage(self._filename)  # 首次访问才真正加载
        self._real_image.display()
```

`main()` 创建 3 个代理但只访问其中 2 个，验证「未访问的图片从未触发加载」。

| 文件 | 说明 |
|------|------|
| `main.py` | `Image` 抽象主题、`RealImage` 真实主题、`ImageProxy` 虚拟代理、`main()` 演示懒加载与缓存 |


## 要点

1. **接口透明** —— 客户端持有的是 `Image` 类型（`gallery: list[Image]`），根本不知道背后是代理还是真实对象。
2. **延迟开销** —— 只有真正调用 `display()` 才会触发耗时的加载逻辑，未访问的对象永远不会付出这份开销。
3. **代理内建缓存** —— 第二次调用同一个代理的 `display()` 时直接复用已加载的 `RealImage`，天然具备缓存代理的效果。
4. 与装饰器的区别：代理控制"是否/何时/如何"访问真实对象（关注访问控制），装饰器关注"叠加职责"；两者结构相似但意图不同。
