# Chain of Responsibility 责任链模式（C++）

## 意图

使多个对象都有机会处理请求，从而避免请求的发送者和接收者之间的耦合关系。将这些对象连成一条链，并沿着这条链传递请求，直到有对象处理它为止。

## 适用场景

- 有多个对象可以处理同一请求，具体由哪个对象处理在运行时才能确定
- 想在不明确指定接收者的情况下，向多个对象中的一个提交请求
- 处理者的集合及顺序应该能够动态变化（如按需插入/移除审批环节）

## 实现方式

`Approver` 是抽象处理者，持有下一环节的指针 `next_` 与自己的审批额度 `limit_`；`handle()` 是非虚的模板骨架：能处理就处理，不能就转交下一环；`can_approve()` 是子类可定制的判断逻辑：

```cpp
void Approver::handle(const PurchaseRequest& request) const {
    if (can_approve(request.amount)) {
        // 批准
    } else if (next_) {
        next_->handle(request);   // 转交责任链的下一环
    } else {
        // 无人能处理
    }
}
```

`Manager`、`Director` 按固定额度判断，`CEO` 重写 `can_approve()` 恒返回 `true`，作为链的兜底。

## 文件说明

| 文件 | 说明 |
|------|------|
| `approval.h` | 请求 `PurchaseRequest`、抽象处理者 `Approver`、三个具体处理者的声明 |
| `approval.cpp` | 链式转交逻辑与各级审批判断的实现 |
| `main.cpp` | 组装“经理->总监->CEO”责任链，提交三笔不同金额的采购申请 |
| `Makefile` | 编译与运行 |

## 编译与运行

```bash
make        # 编译
make run    # 编译并运行
make clean  # 清理
```

## 要点

1. **发送者与接收者解耦** — 客户端只需要拿到链的第一环（`manager`），不需要知道最终是谁处理的
2. **链的组装是运行时行为** — `set_next()` 可以在运行时调整链的结构和顺序
3. **每个处理者职责单一** — 只关心“自己能不能处理”，转交逻辑在基类中统一实现，子类无需重复
4. **注意链的完整性** — 若没有任何环节能处理且链末端也不兜底，请求会被“默默地”忽略，需要显式的兜底处理者（如本例的 CEO）
