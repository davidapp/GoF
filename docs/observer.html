观察者模式 Observer

一句话：一个东西变了，所有盯着它的人会自动收到通知。它还有个更形象的名字——"发布/订阅"。

← 上一个备忘录模式 下一个 →状态模式

🌰 生活里的例子

微信公众号

你关注了一个公众号，博主发新文章时，所有粉丝都会自动收到推送；不感兴趣了随时取关，之后就再也收不到消息。

注意一个细节：博主根本不认识你，也不知道粉丝都有谁，他只管"发文"这一个动作。但只要他发了，消息就能精准送到每个粉丝手上——因为公众号后台替他记住了"谁订阅了我"这份名单。

观察者模式干的就是这件事：被观察的人只管宣布"我变了"，名单上的人自动收到消息。双方谁也不认识谁，全靠一份订阅名单联系。

😖 没有它会怎样

假设有一个气象站，每分钟采集一次温度。手机 App、路口的电子广告牌、农场的大棚系统都想要这份温度数据。最直接的写法：

直来直去的写法（问题代码）

气象站每次测到新温度，就直接挨个调用：

phoneApp.update(temp) → billboard.show(temp) → farmSystem.check(temp) ……

这样写眼下能跑，但麻烦在后头：

  • 加一个显示设备，就得改一次气象站的代码。下个月新来了个"手表 App"？对不起，气象站得重新开膛破肚。
  • 气象站被迫认识所有设备，谁跟谁都缠在一起，牵一发而动全身。
  • 想临时下线某个设备？还是得改气象站。

根子上的问题是方向反了：不该是"数据的主人追着喂给所有人"，而应该是"想吃的人自己来订"。

👥 角色构成（这个模式由几块拼成）

角色大白话职责本仓库示例里是谁
主题 Subject（被观察者） 定规矩的人：提供"订阅、退订、广播"三个方法，好比公众号后台。 WeatherSubject 接口
具体主题 真正持有数据的人。数据一变，就拿起名单挨个打电话。 WeatherStation（气象站）
观察者 Observer 定一个约定："收到消息后请调你的 update()"。只约定格式，不管你具体干什么。 WeatherObserver 接口
具体观察者 订阅方。各自决定收到温度后干什么：手机推送、广告牌换字…… PhoneDisplay、BillboardDisplay

注意：气象站只认识"观察者接口"，不认识任何具体设备。这就是解耦的关键——只要你是观察者（实现了 update），我就通知你，至于你是谁、干什么用的，我一概不问。

🗺️ 结构图（谁认识谁、谁调用谁）

WeatherStation具体主题 · 拿着订阅名单
通知
逐个调 update()
PhoneDisplay手机 App
BillboardDisplay电子广告牌

箭头方向 = 调用方向：只有主题调用观察者；反过来，观察者只在进门时调用一次 subscribe()。

🔄 运转步骤（跑一遍完整流程）

  1. 订阅：手机 App 调用 station.subscribe(自己)，气象站把它记进名单。
  2. 再订阅：广告牌、农场系统也先后来订阅，名单越来越长。
  3. 数据变了：气象站测到新温度 26.5°C。
  4. 广播：气象站遍历名单，挨个调用 update(26.5)——每个设备用自己的方式展示。
  5. 退订：广告牌下班了，调用 unsubscribe(自己)，从此收不到通知，气象站毫发无损。

🔍 代码走读

下面是本仓库 TypeScript 实现的骨架（完整版见 ts/observer/main.ts，有删减）：

ts/observer/main.ts（简化）
// 观察者接口：只约定"收到消息怎么办"
interface WeatherObserver {
  update(temperature: number, humidity: number): void;
}

// 具体主题：拿着名单，数据一变就广播
class WeatherStation {
  private readonly observers: WeatherObserver[] = [];  // 订阅名单

  subscribe(o: WeatherObserver): void { this.observers.push(o); }   // ① 进名单

  unsubscribe(o: WeatherObserver): void {                            // ⑤ 出名单
    const i = this.observers.indexOf(o);
    if (i !== -1) this.observers.splice(i, 1);
  }

  private notify(): void {                                           // ④ 广播
    for (const o of this.observers) o.update(this.temperature, this.humidity);
  }

  // ③ 数据一变，顺手广播
  setMeasurements(t: number, h: number): void {
    this.temperature = t;
    this.humidity = h;
    this.notify();
  }
}

// 具体观察者：收到消息后自己决定干什么
class PhoneDisplay implements WeatherObserver {
  update(temperature: number): void {
    console.log(`[手机] 推送：现在 ${temperature}°C`);
  }
}

看懂这段代码，就看懂了整个模式

整个模式的核心其实就三行：一个数组（名单）+ 订阅时 push + 通知时遍历调用。剩下的都是把这三行包装得更安全、更好维护。

⚖️ 什么时候用，什么时候别用

✅ 适合的场景

  • 一个东西变了，多个地方都要跟着动，而且"哪些地方"经常增减
  • 事件系统：按钮点击、消息到达、数据更新……框架里到处都是它
  • 不想让数据的主人认识所有使用方（解耦）

❌ 不适合的场景

  • 联动对象只有一两个且固定不变——直接调用反而更清楚
  • 各观察者之间有严格的先后顺序——通知顺序没有保证，会埋雷
  • 需要"一问一答"式交互——那是请求响应，不是广播

⚠️ 容易踩的坑

  • 忘了退订 → 内存泄漏。名单一直攥着观察者不放，对象永远删不掉。页面/组件销毁时记得 unsubscribe。
  • 观察者在 update 里反过来改主题 → 死循环。A 通知 B，B 又改 A，A 再通知 B……栈直接爆掉。
  • 通知是同步串行的。名单里有个观察者干活特别慢，数据主人就得干等它——慢的应该丢到队列里异步处理。
  • 广播之后不知道谁干了什么。排查问题时记日志：通知了谁、谁报错了。

🔗 和其他模式的关系

  • 和中介者模式最容易混：观察者是"一个喇叭对多头广播"，单向的；中介者是"一群人互相聊天，全通过中间人"，多向的。
  • 主题有时被做成单例（比如全局的事件总线），保证大家订阅的是同一个名单。
  • 观察者本身常用策略模式的思路实现——"收到消息后怎么办"就是可替换的策略。
一 句 话 记 住 它 订阅它，它变了就自动喊你；取关了，它就当你不存在。
