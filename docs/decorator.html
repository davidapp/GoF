装饰器模式 Decorator

一句话：像穿衣服：本体一个字不改，一层层往外套，每套一层加一点本事，随时可穿可脱。

← 上一个组合模式 下一个 →外观模式

🌰 生活里的例子

冬天出门穿衣服

你要出门（客户端调用）。出门前先穿上打底（本体），觉得冷，套件毛衣（装饰器一层）；还是冷，再套件羽绒服（装饰器又一层）；下雨了，最外面再罩件雨衣（第三层）。

注意两个细节：你还是你，穿再多衣服，出门的还是这个人，接口没变；每件衣服只管加自己那点功能——毛衣不管防雨，雨衣不管保暖，谁也不掺和谁的活。

对应到模式里：打底是"具体组件"，每件衣服是一个"装饰器"，"我这个人"就是大家共享的接口。想加功能就多套一层，想换搭配就换个穿法，衣柜（类库）本身不用重新生产。

😖 没有它会怎样

本仓库的例子是咖啡定价：一杯 Espresso 18 元，可以加牛奶 +4、糖浆 +2、奶油 +6。如果靠继承给每种搭配造一个类：

直来直去的写法（问题代码）

为每种组合各生一个子类：

Espresso、EspressoWithMilk、EspressoWithSugar、EspressoWithMilkAndSugar、EspressoWithDoubleMilkAndCream ……

三种配料就有 8 种组合，麻烦在后头：

  • 每加一种配料，子类数量直接翻倍——这是乘法，不是加法，越长越吓人。
  • 搭配是写死在类型里的，客人说"奶油去掉"？做不到，只能整个换一种类重新点。
  • 价格、描述两套逻辑在十几个子类里抄来抄去，改个牛奶价钱要动一半的类。

根子上的问题是：把"组合"当成了"种类"去继承，而组合是运行时随手拼的事。

👥 角色构成（这个模式由几块拼成）

角色大白话职责本仓库示例里是谁
组件 Component 共同身份：定下"是一杯咖啡"就得会算钱、会自报配料。 Coffee 接口（cost / description）
具体组件 被包装的本体：打底那件，什么料都没加。 Espresso（18 元）
抽象装饰器 关键中间层：自己实现 Coffee，怀里又揣一个 Coffee，默认原样转发——衣服的"通用版型"。 CoffeeDecorator
具体装饰器 各种料：在转发的基础上加自己的价钱和名字，每件只管自己。 MilkDecorator、SugarDecorator、WhippedCreamDecorator

解耦（把缠在一起的代码拆开，互不认识也能合作）关键在：装饰器和本体实现同一个接口——所以装饰器怀里揣的既可以是本体，也可以是另一个装饰器（毛衣外面套羽绒服）；而客户端拿到的永远是 Coffee，包了三层它也察觉不到，更不关心。

调用从最外层钻进去，像剥洋葱一样一层层往里传，结果再一层层加出来——每一层只认识"怀里的那个 Coffee"，不认识整条链。

🔄 运转步骤（跑一遍完整流程）

  1. 点本体：order = new Espresso()，此刻 18 元，描述"Espresso"。
  2. 套一层：order = new MilkDecorator(order)——注意套的还是刚才那个 order，现在它 22 元。
  3. 再套：order = new SugarDecorator(order)，24 元；喜欢的话还能接着套奶油。
  4. 调用：order.cost() 从最外层进入，糖浆先问牛奶"你多少？"，牛奶再问咖啡"你多少？"。
  5. 层层加价：咖啡答 18，牛奶加 4 报 22，糖浆加 2 报 24——一层层传回来，账算完了；description() 同理拼出"Espresso + 牛奶 + 糖浆"。
  6. 互不干扰：另点一杯双糖，new SugarDecorator(new SugarDecorator(new Espresso()))，原来那杯单子纹丝不动。

🔍 代码走读

下面是本仓库 TypeScript 实现的骨架（完整版见 ts/decorator/main.ts，有删减）：

ts/decorator/main.ts（简化）
// 组件接口：一杯咖啡会算钱、会自报家门
interface Coffee {
  cost(): number;
  description(): string;
}

// 具体组件：打底的 Espresso
class Espresso implements Coffee {
  cost() { return 18; }
  description() { return "Espresso"; }
}

// 抽象装饰器：自己也实现 Coffee，怀里再揣一个 Coffee，默认原样转发
abstract class CoffeeDecorator implements Coffee {
  constructor(protected readonly coffee: Coffee) {}
  cost() { return this.coffee.cost(); }
  description() { return this.coffee.description(); }
}

// 具体装饰器：在转发的基础上加自己的料
class MilkDecorator extends CoffeeDecorator {
  cost() { return super.cost() + 4; } // 里层价格 + 4
  description() { return `${super.description()} + 牛奶`; }
}

class SugarDecorator extends CoffeeDecorator {
  cost() { return super.cost() + 2; }
  description() { return `${super.description()} + 糖浆`; }
}

// 层层包裹：Espresso -> 加奶 -> 加糖，拿到的还是 Coffee
let order: Coffee = new Espresso();
order = new MilkDecorator(order);
order = new SugarDecorator(order);
console.log(order.description(), order.cost()); // 24 元

看懂这段代码，就看懂了整个模式

全部秘密在抽象装饰器那三行：实现同一接口 + 持有同接口引用 + 默认转发。正因为"装饰器也是 Coffee"，它才能包住任何 Coffee，包括另一个装饰器——套娃合法了。

⚖️ 什么时候用，什么时候别用

✅ 适合的场景

  • 想运行时动态增减职责：加料、加缓存、加日志、加重试，套一层的事
  • 职责的组合方式很多，用继承会子类爆炸（本例 3 种料 8 种组合）
  • 不能或不想改原类（类是 final 的、第三方提供的）

❌ 不适合的场景

  • 搭配就固定一两种——直接继承一个子类，反而一眼看穿
  • 代码里靠 instanceof 认"真实类型"——包装后认不出本体，逻辑会翻车
  • 各层职责互相依赖、顺序极度敏感——调试地狱，不如老老实实写清楚

⚠️ 容易踩的坑

  • 装饰顺序敏感。先打折再加税和先加税再打折，账差一截。本例价格是加法所以没事，但描述的先后顺序还是不一样——顺序有语义时要当心。
  • 调试像剥洋葱。断点打进去，类型是一长串包装，看不出本体是什么；日志里多打几层描述能救命。
  • 和 TS 的 @decorator 搞混。那是语言级语法（编译期改类定义），GoF 装饰器是运行时对象包装，同名不同物。
  • 装饰器里写死了本体类型。怀里只肯揣 Espresso 不肯揣 Coffee——套娃直接断了，模式废掉。

🔗 和其他模式的关系

  • 和代理模式是结构双胞胎：都是"同接口 + 持引用 + 转发"。区别在意图——装饰器是主动叠加职责、可以多层；代理是控制访问、通常一层，客户端还不知道有真身。
  • 和组合模式是一家：装饰器是"包一个"，组合是"装一群"，都靠"实现同一接口"让外界无感。
  • 如果只是"同一件事换种做法"而不是"往上叠加"，用策略模式更省事。
一 句 话 记 住 它 本体不动，一层层套：每层加点料，脱掉也不伤身。
