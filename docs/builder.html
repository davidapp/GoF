建造者模式 Builder

一句话：把"一口气传一堆参数"变成"一步一步设"，最后 build() 一下拿成品。

← 上一个抽象工厂模式 下一个 →工厂方法模式

🌰 生活里的例子

奶茶店点单

店员不会让你一口气背出"中杯茉莉奶绿三分糖去冰加珍珠加椰果"，而是一步一步问你：杯型？茶底？甜度？冰量？加料？你答一步她做一步，最后封口，递给你一杯完整的奶茶。

嫌麻烦？直接说"来杯店长推荐"——店员照着官方配方唰唰做完，你一步都不用操心。

对应到模式里：奶茶是产品（Computer），每个问题是 builder 的一个 set 方法（setCpu、setRam），封口出货是 build()，"店长推荐"就是指挥者 Director 的预设方法（buildOfficePC）。想按官方配方来就找 Director，想自由发挥就自己一步步 set。

😖 没有它会怎样

本仓库的示例是攒电脑：CPU、内存、存储、显卡，四大件各有讲究。最直接的写法是一个巨大的构造函数：

直来直去的写法（问题代码）

new Computer("Intel i9", "32GB", "2TB NVMe SSD", "RTX 4090")

现在才 4 个参数。想象字段涨到十几个，其中一半还是可选的呢？

这样写的麻烦：

  • 调用处全是裸字符串：看代码的人根本不知道第 3 个参数是存储还是显卡，传错位置编译器也不吭声。
  • 可选参数只能拿 undefined 占位：只想设显卡？对不起，前面几个先填一串空。
  • "办公配置"这种常用套餐被抄了 N 遍：每个调用处都重新抄一遍参数，想统一改配置？满项目找。
  • 没法分步校验：比如"选了顶配显卡才允许上大电源"这种规则，塞一个构造函数里写起来很难受。

根子上的问题是"怎么填字段"和"填哪些值"被焊死在一次调用里，拆开来才好收拾。

👥 角色构成（这个模式由几块拼成）

角色大白话职责本仓库示例里是谁
产品 Product 最终要攒出来的复杂家伙。 Computer
建造者接口 Builder 把"攒货的每一步"都列成一个方法，最后加一个出货方法。 IComputerBuilder 接口
具体建造者 真正动手攒；每个 set 方法都 return this，所以能一路"点"下去（链式调用）。 ComputerBuilder
指挥者 Director 记配方的人：把"常见套餐"封装成一个方法，照方抓药。 ComputerDirector（buildOfficePC()、buildGamingPC()）
客户端 顾客：点套餐找 Director，自由发挥直接找 Builder。 main() 里的调用代码

解耦关键："字段怎么填"（Builder 的 set 方法）、"按什么配方填"（Director）、"填成个啥"（Computer）三件事被拆开了。换个配方不用动 Builder，换个攒法不用动产品，各改各的互不牵连。

🗺️ 结构图（谁认识谁、谁调用谁）

箭头方向 = 调用方向：客户端站在最左端——走套餐就经过 Director，自由配就绕过它直接指挥 Builder；两条路最后都从 build() 拿货。

🔄 运转步骤（跑一遍完整流程）

  1. 备料：new ComputerBuilder()，会攒电脑的师傅就位，内部先备好一台空 Computer。
  2. 请指挥者（可选）：new ComputerDirector(builder)，把师傅交给记配方的人。
  3. 点套餐：调 director.buildGamingPC()，它按配方依次 setCpu("Intel i9")、setRam("32GB")……
  4. 链式设置：每个 set 方法最后都 return this，所以能写成 builder.setCpu(…).setRam(…).setStorage(…) 一条链。
  5. 出货：调 build()，把攒好的 Computer 交出来；builder 顺手把内部状态重置，下次再用不串台。
  6. 自由发挥：不想点套餐？跳过 Director，自己对着 builder 一路 set，最后 build()，怎么配随你。

🔍 代码走读

下面是本仓库 TypeScript 实现的骨架（完整版见 ts/builder/main.ts，有删减）：

ts/builder/main.ts（简化）
// 产品：最终要攒出来的家伙
class Computer {
  cpu = "未指定";
  ram = "未指定";
  storage = "未指定";
  gpu?: string;   // 可选：不装独显
}

// 建造者：每个 set 都 return this，才能链式一路点下去
class ComputerBuilder implements IComputerBuilder {
  private computer = new Computer();

  setCpu(cpu: string): this { this.computer.cpu = cpu; return this; }
  setRam(ram: string): this { this.computer.ram = ram; return this; }
  setStorage(s: string): this { this.computer.storage = s; return this; }
  setGpu(gpu: string): this { this.computer.gpu = gpu; return this; }

  build(): Computer {
    const result = this.computer;
    this.computer = new Computer();  // 重置，避免下次构建被污染
    return result;
  }
}

// 指挥者：把常见套餐封装成一个方法
class ComputerDirector {
  constructor(private readonly builder: IComputerBuilder) {}

  buildGamingPC(): Computer {
    return this.builder
      .setCpu("Intel i9")
      .setRam("32GB")
      .setStorage("2TB NVMe SSD")
      .setGpu("NVIDIA RTX 4090")
      .build();                     // 最后一步：出货
  }
}

看懂这段代码，就看懂了整个模式

建造者的魂就两样：一堆返回 this 的 set 方法（链式）+ 一个 build() 出货。Director 只是可选配件——它把"常用配方"背下来了而已，本仓库特意演示了绕开它自由配的那条路。

⚖️ 什么时候用，什么时候别用

✅ 适合的场景

  • 构造参数多、可选参数多，构造函数已经变成"望远镜"（参数一个套一个越传越长）
  • 同一套攒法要产出多种成品（办公机 / 游戏机 / 服务器）
  • 构造过程要分步进行、分步校验，或者要复用"标准配方"

❌ 不适合的场景

  • 字段就两三个——直接构造函数，三行搞定的事别写三十行
  • 对象简单、字段固定必填——一个 new 就是最优解
  • 只是想复制一份现成的对象——那是原型模式的活儿

⚠️ 容易踩的坑

  • 忘了调 build()。光链式 set 了半天，拿到的其实是 builder 自己而不是产品，一用类型就对不上。链式写得太顺，这个错特别容易犯。
  • 复用 builder 忘了重置。本仓库的 build() 里特意换了个新 Computer；自己实现时漏掉这步，第二次攒的机器会带上一次的残留零件。
  • 链式调用不保证顺序。有的步骤有先后依赖（先装主板再插显卡），链式写法一句报错都没有，全靠调用者自觉。
  • 简单对象硬上建造者。三个字段的小类套上四层结构，属于为模式而模式，读代码的人反而更累。

🔗 和其他模式的关系

  • 和工厂方法模式分工明确：工厂是"一步到位给成品"，建造者是"分好几步攒成品"。要标准品找工厂，要精细定制找建造者。
  • 攒到一半的配置想"存个底稿以后复印"？把当前成品当原型克隆一份，就轮到原型模式出场。
  • 可以和抽象工厂模式合体：工厂负责选"哪家厂的套件"，建造者负责"怎么一步步装起来"。
一 句 话 记 住 它 一步一步设，build() 出成品；懒人直接点套餐（Director）。
