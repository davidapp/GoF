工厂方法模式 Factory Method

一句话："造哪个"这件事父类不定死，留个空让子类自己填。

← 上一个建造者模式 下一个 →原型模式

🌰 生活里的例子

连锁快递的总部与网点

你在 App 上下单，总部有一套写死的流程：接单 → 派车 → 取件 → 送达。但"派车"这一步总部故意留空：市区网点派电动车，郊区网点派卡车，海岛网点干脆派船。你寄同一个快递到不同地方，走的流程一模一样，跑腿的车却由各地网点自己定。

总部只立了规矩："每个网点必须能派出一辆会送货车。"至于是烧油还是烧电、走公路还是走海路，网点说了算。

对应到模式里：总部的流程是 Logistics.planDelivery()（抽象创建者的公共方法），留空的"派车"就是工厂方法 createTransport()，各地网点是具体创建者（RoadLogistics、SeaLogistics），车是具体产品（Truck、Ship）。

😖 没有它会怎样

本仓库的示例是物流系统：不管陆运海运，"规划配送"的流程是一样的，只有用的运输工具不同。最直接的写法，是在公共流程里现场判断类型：

直来直去的写法（问题代码）

planDelivery() 里写：

if (type === "road") t = new Truck();
else if (type === "sea") t = new Ship();

以后每加一种运输方式，就回来加一个分支。

这样写的麻烦：

  • 每加一种运输方式就得改公共流程：空运、铁路、无人机……改一次流程，所有路线都得重新测一遍。
  • "流程"和"选车"缠在一个函数里：想单独复用流程？甩不掉那一坨 if。
  • 判断逻辑到处复制：十个地方都要"拿一辆车"，就抄十段 if，改漏一处就是 bug。

根子上的问题是选择权攥在了流程手里，而它本该下放给"专门负责造车的人"。

👥 角色构成（这个模式由几块拼成）

角色大白话职责本仓库示例里是谁
抽象产品 Product 立合同："是运输工具，就得会送货。" Transport 接口
具体产品 真正跑腿的：卡车、轮船。 Truck、Ship
抽象创建者 Creator 流程骨架写死，中间挖一个"造车"的空。 Logistics 抽象类（planDelivery()）
工厂方法 那个空本身，专门负责"造出产品"这一个动作。 createTransport()
具体创建者 子类只干一件事：把空填上，返回自己族的产品。 RoadLogistics、SeaLogistics

解耦关键：planDelivery() 只认识 Transport 接口，不认识卡车轮船任何一辆车。以后新增运输方式 = 新增一对子类，公共流程零改动——这就是开闭原则（对扩展开门，对修改关门）落地的样子。

🗺️ 结构图（谁认识谁、谁调用谁）

箭头方向 = 调用方向：客户端只 new 一个具体创建者、调 planDelivery()；父类流程"回头调用"子类填空的结果——这就是"把决定权延迟到子类"。

🔄 运转步骤（跑一遍完整流程）

  1. 选网点：new RoadLogistics()，决定这条线路归谁管。
  2. 启动流程：调 planDelivery()，这套流程是父类 Logistics 写死的，所有网点共用。
  3. 跑到空位：流程内部调 this.createTransport()——一个抽象方法，父类自己不实现。
  4. 子类填空：RoadLogistics 的实现返回 new Truck()，运力到位。
  5. 干活：流程拿到 Transport 后立刻调 deliver()，从头到尾不知道也不关心它是卡车还是轮船。
  6. 扩路线：明天要空运？新加 AirLogistics 和 Plane 两个类，老代码一行不动。

🔍 代码走读

下面是本仓库 TypeScript 实现的骨架（完整版见 ts/factory-method/main.ts，有删减）：

ts/factory-method/main.ts（简化）
// 抽象产品：立合同，"运输工具都得会送货"
interface Transport {
  deliver(): string;
}

// 具体产品：真正跑腿的
class Truck implements Transport {
  deliver(): string { return "使用卡车经陆路运输货物"; }
}
class Ship implements Transport {
  deliver(): string { return "使用轮船经海路运输货物"; }
}

// 抽象创建者：流程写死在这里，"造哪个车"留给子类
abstract class Logistics {
  protected abstract createTransport(): Transport;  // 工厂方法（空位）

  planDelivery(): string {              // 公共流程，与具体车型无关
    const transport = this.createTransport();
    return `[规划配送] ${transport.deliver()}`;
  }
}

// 具体创建者：只回答"用什么车"这一个问题
class RoadLogistics extends Logistics {
  protected createTransport(): Transport { return new Truck(); }
}
class SeaLogistics extends Logistics {
  protected createTransport(): Transport { return new Ship(); }
}

看懂这段代码，就看懂了整个模式

整个模式的核心画面就一句话：父类流程里留了一个"造产品"的空方法，子类负责填。planDelivery() 全程只见 Transport 接口，所以加多少种车它都不用改。

⚖️ 什么时候用，什么时候别用

✅ 适合的场景

  • "该造哪个具体类"要由子类在运行时说了算，父类定不了
  • 有一套与产品无关的公共流程要复用（本例的规划配送）
  • 希望新增产品时只加类、不改旧代码（开闭原则）

❌ 不适合的场景

  • 只有一种实现、 foreseeable 也不会变——直接 new 就完了
  • 产品选择用一两个分支就能搞定、且不会膨胀——别硬造四层类
  • 只是想封装一下 new、根本不需要子类体系——一个工厂函数就够

⚠️ 容易踩的坑

  • 类爆炸。每种产品都要配一个创建者子类，产品一多，文件数量直接翻倍，目录看着就头大。
  • 和"简单工厂"搞混。简单工厂是一个类里写 if/switch 选产品；工厂方法没有 if，是把选择权通过继承下放给子类。两者不是一回事。
  • 父类流程的隐含契约。子类返回的产品必须真能干活（有 deliver() 的完整实现），返回个半成品流程照样跑，锅在运行时才爆。
  • 为了"消灭 if"而用。分支就两三个、且稳定不变时，直接写 if 反而最清楚，套模式属于过度设计。

🔗 和其他模式的关系

  • 和抽象工厂模式的区别是面试必考：工厂方法靠继承、造"一个"产品；抽象工厂靠组合（把工厂对象传进来）、造"一族"产品。
  • planDelivery() 这种"骨架写死、细节留空"的写法，就是模板方法模式的味道，两者经常成对出现。
  • 工厂方法内部可以改用克隆来"造"产品：持有一份原型，每次返回 clone()——这是和原型模式的常见合体方式。
一 句 话 记 住 它 流程爸爸定死，"造啥"留个空让儿子填。
