责任链模式 Chain of Responsibility

一句话：把几个处理者串成一条链，请求顺着链往下递，谁能办谁接手；发请求的人只管递出去，根本不用认识最后是谁办的。

🌰 生活里的例子

打客服电话被层层转接

你家宽带出问题了，打客服电话。一线客服查了查：办不了，"帮您转技术组"；技术组检测完发现是线路老化，也办不了，"帮您转装维师傅"；最后师傅上门，事办成了。

整个过程你只拨了一个号码，根本不知道、也不关心最后是谁解决的。每一级客服只做两件事：能办就办，办不了转给下一级。

这个比喻对应模式里的什么：一线客服、技术组、师傅 = 链上的一个个处理者；"转接" = 处理者手里的下家引用（谁的下家是谁，接线时就连好了）；你 = 发请求的客户端，只认识第一个接电话的人。

😖 没有它会怎样

本仓库的场景是采购审批：金额小的经理批，大点的总监批，再大的 CEO 批。最直接的写法是在提交申请的地方堆一坨 if/else：

直来直去的写法（问题代码）

提交申请时挨个问一遍：

if (amount <= 1000) managerApprove(r) → else if (amount <= 10000) directorApprove(r) → else ceoApprove(r) ……

这样写眼下能跑，但麻烦在后头：

  • 审批规则一变就得改这里。经理上限涨到 2000？插入一个"副总监"？全得回来改 if/else，改漏一处就乱套。
  • 提交申请的代码被迫认识所有审批人，跟人事架构死死焊在一起——人事一动，代码跟着动。
  • 同样的金额判断逻辑到处复制：网页端写一遍、审批流又写一遍，永远改不齐。

根子上的问题是方向反了：不该让发请求的人决定"谁有资格处理"，应该让处理者们自己排好队，请求自己往下流。

👥 角色构成（这个模式由几块拼成）

角色大白话职责本仓库示例里是谁
处理者 Handler 定规矩的人："能办就办，办不了转给下家"。手里攥着下家的联系方式。 Approver 抽象类
具体处理者 真正干活的。每人只需回答一个问题："多大金额我能批？" Manager（≤¥1,000）、Director（≤¥10,000）、CEO（无上限）
请求 沿链流动的数据包：这笔申请要多少钱、干什么用。 PurchaseRequest 接口
客户端 只负责拼链 + 把请求交给链头，之后的事一概不知。 main() 函数

解耦关键在哪：提交人只认识链头（Manager），每个审批者只认识自己的下家。想插入一个"副总监"？写个新类、重新 setNext() 拼一次链就行，Approver 和其他审批者一行代码都不用改——这就是解耦（把缠在一起的代码拆开，互不认识也能合作）。

每个箭头都是一句"我权限不够，交给你"。谁也不认识整条链，只认识自己的下家；一路传到链尾还没人能办，就要明确"拒绝"，不能让申请悄悄消失。

🔄 运转步骤（跑一遍完整流程）

  1. 拼链：manager.setNext(director).setNext(ceo)，三级审批链连好了（setNext 返回下家，正好链式写）。
  2. 提交：一笔"办公用品采购 ¥500"交给链头 manager.handle(request)。
  3. 经理接手：500 ≤ 1000，权限够，直接批准。
  4. 逐级上交：来了一笔"服务器采购 ¥80,000"，经理权限不够转总监，总监也不够再转 CEO，CEO 无上限，批准。
  5. 兜底：万一请求传到链尾还是没人能办（本例 CEO 无上限所以不会发生），打印"申请被拒绝"——宁可明说，不能装没看见。

🔍 代码走读

下面是本仓库 TypeScript 实现的骨架（完整版见 ts/chain-of-responsibility/main.ts，有删减）：

ts/chain-of-responsibility/main.ts（简化）
// 抽象处理者：能办就办，办不了转给下家
abstract class Approver {
  private next: Approver | undefined;

  setNext(next: Approver): Approver {   // 返回 next，方便链式拼接
    this.next = next;
    return next;
  }

  handle(request: PurchaseRequest): void {
    if (this.canApprove(request.amount)) {
      console.log(`${this.getTitle()} 批准了 [${request.purpose}]，金额 ¥${request.amount}`);
    } else if (this.next !== undefined) {
      console.log(`${this.getTitle()} 权限不足，转交上级审批...`);
      this.next.handle(request);        // 关键一步：把请求递给链的下一站
    } else {
      console.log(`超出所有审批人的权限，申请被拒绝`);  // 链尾兜底
    }
  }

  protected abstract canApprove(amount: number): boolean;
  protected abstract getTitle(): string;
}

// 具体处理者：只回答"我的权限上限是多少"
class Manager extends Approver {
  protected canApprove(amount: number): boolean { return amount <= 1_000; }
  protected getTitle(): string { return "部门经理"; }
}

// 客户端：拼链，然后把请求交给链头
manager.setNext(director).setNext(ceo);
manager.handle({ amount: 80_000, purpose: "服务器采购" });

看懂这段代码，就看懂了整个模式

整个模式的核心就是 handle() 里那个 else 分支的一行递归调用：this.next.handle(request)。请求就这样一站一站往下传，谁有本事谁截停。剩下的代码都是在定义"每一站的本事"。

⚖️ 什么时候用，什么时候别用

✅ 适合的场景

  • 同一个请求有好几个人能处理，具体谁来办要到运行时才见分晓（按金额、按级别、按类型）
  • 处理者经常增减、顺序经常调整——重新拼一次链就行，谁也不用改
  • 发请求的一方不想（也不该）认识所有处理者

❌ 不适合的场景

  • 处理者永远只有一个且固定——直接调用最清楚，链是累赘
  • 请求必须保证被处理、调用方还要拿到处理结果——链式传递容易"传丢了没人管"
  • 性能敏感的热点路径——长链上一个一个问过去，白花时间

⚠️ 容易踩的坑

  • 链尾没人兜底 → 请求无声消失。传到最后没人能办，也不吭声，申请就石沉大海。本例在链尾明确打印"被拒绝"——宁可明说，不可装没看见。
  • 链拼错或拼断。setNext 忘了连、顺序连反（把 CEO 排在经理前面），程序照跑但结果全错。拼链的代码要集中在一处，别散落各文件。
  • 把链当流水线什么都塞。处理者又改数据又发通知，一个节点出事整条链遭殃。每个节点只干"我能不能办"这一件事。
  • 调试没痕迹。请求走到哪一步了全靠猜。每个节点的"转交"处都该打日志（本例就打了"权限不足，转交上级"）。

🔗 和其他模式的关系

  • 和命令模式是好搭档：命令把请求打包成对象，责任链让一串处理者轮流接手这个对象，直到有人执行。
  • 链上的节点本身可以又是一棵组合模式的树——大链套小链，子链处理完再交上级。
  • 和观察者模式方向不同：观察者是"一个消息广播给所有人听"，责任链是"一个请求接力传下去，有一个人接住就停"。
一 句 话 记 住 它 能办就办，办不了往上报；发申请的人，只管把单子递进第一个窗口。
