迭代器模式 Iterator

一句话：请一位导游带你挨个参观集合里的元素，集合内部到底是怎么摆放的，你一概不用知道。

← 上一个解释器模式 下一个 →中介者模式

🌰 生活里的例子

博物馆的讲解员

你参观博物馆，不需要仓库钥匙，也不用知道哪件展品锁在哪个柜子——只要跟着讲解员走。讲解员心里有一条路线：带你看一件，再看下一件。你只管问一句"还有吗？"（有），他就带你看下一个。看完了，他说"没了"，参观结束。

朋友中途加入、想从头看一遍？再领一位讲解员就是——两条路线各走各的，互不干扰。讲解员哪天调整路线（先看青铜器再看瓷器），你照样跟着走，看法一点没变。

这个比喻对应模式里的什么：讲解员 = 迭代器（BookIterator），他记的"走到第几件" = 游标 index；博物馆 = 聚合（BookCollection），展柜怎么布局（数组还是链表）你不知道也不用知道；"还有吗 / 下一个" = hasNext() / next()；再领一位讲解员 = 再 createIterator() 一个，多个遍历同时进行、互不踩脚。

😖 没有它会怎样

本仓库的场景是图书藏书：BookCollection 里存着一堆书，外部想挨本翻一翻。最直接的写法是让集合把内部家底直接交出来：

直来直去的写法（问题代码）

集合暴露内部数组，调用方自己按下标遍历：

const books = library.getBooks(); 然后 for (let i = 0; i < books.length; i++) { ... }

这样写眼下能跑，但麻烦在后头：

  • 内部结构彻底暴露："我用数组存的"成了公开秘密。哪天想换成链表、换成数据库懒加载，所有调用方代码全得改。
  • 想两个人同时遍历？游标没地方放——放在集合身上只有一份，A 走到第 2 本，B 就只能从第 3 本接着看。
  • 各种集合各自发明遍历写法：书架一套、队列一套、树又一套，调用方每换一种集合就得学一套新招。

根子上的问题是把"怎么存"和"怎么走"搅在一起了。拆开的办法：集合继续管存，另请一位"导游"专门管走。

👥 角色构成（这个模式由几块拼成）

角色大白话职责本仓库示例里是谁
抽象迭代器 定规矩："导游只要会两招——还有吗（hasNext）、下一个（next）"。 CustomIterator<T> 接口
具体迭代器 真导游。自己保管游标，替集合跑腿，一个元素一个元素往外递。 BookIterator
抽象聚合 定规矩："想被遍历？请提供 createIterator() 发导游"。 Aggregate<T> 接口
具体聚合 博物馆本体。数据怎么存是它的私事；要几个导游就发几个。 BookCollection（同时实现了 TS 原生的 Iterable<Book> 协议）
元素 被参观的展品。 Book 接口

解耦关键在哪：调用方只认识"hasNext / next"这两个问题，集合只负责发导游，数组下标一个都不外泄。内部今天用数组、明天换链表，调用方代码一字不改——这就是解耦（把缠在一起的代码拆开，互不认识也能合作）。

🔄 运转步骤（跑一遍完整流程）

  1. 装书：library.addBook(...) 放进《设计模式》《重构》《代码整洁之道》三本——内部用数组存，外界不知道。
  2. 领导游：library.createIterator() 得到一个 BookIterator，游标指着第 0 本。
  3. 问：hasNext()——游标还没走到头？有，继续。
  4. 取：next() 返回当前这本，游标悄悄前移一格。
  5. 循环：一问一取，直到 hasNext() 说"没了"，遍历结束。
  6. 换原生姿势再来一遍：同一个 library 直接 for...of 遍历、[...library] 展开——因为它还实现了 Symbol.iterator 协议，这是迭代器在现代语言里的"隐形"形态。

🔍 代码走读

下面是本仓库 TypeScript 实现的骨架（完整版见 ts/iterator/main.ts，有删减）：

ts/iterator/main.ts（简化）
// 抽象迭代器：只约定两个问题——"还有吗"和"给我下一个"
interface CustomIterator<T> {
  hasNext(): boolean;
  next(): T;
}

// 具体迭代器：自己保管游标，替集合跑腿
class BookIterator implements CustomIterator<Book> {
  private index = 0;                    // 游标：现在走到第几本

  constructor(private readonly books: readonly Book[]) {}

  hasNext(): boolean { return this.index < this.books.length; }

  next(): Book {
    if (!this.hasNext()) throw new Error("已到达集合末尾");
    return this.books[this.index++]!;  // 交出当前这本，游标前移
  }
}

// 具体聚合：内部用数组存书，但一个下标都不外泄
class BookCollection implements Aggregate<Book>, Iterable<Book> {
  private readonly books: Book[] = [];

  addBook(book: Book): void { this.books.push(book); }

  createIterator(): CustomIterator<Book> {
    return new BookIterator(this.books);   // 发一个新导游
  }

  // 顺手实现语言原生协议，白得 for...of 和展开运算符
  [Symbol.iterator](): Iterator<Book> {
    let index = 0;
    const books = this.books;
    return {
      next() {
        return index < books.length
          ? { value: books[index++]!, done: false }
          : { value: undefined, done: true };
      },
    };
  }
}

看懂这段代码，就看懂了整个模式

核心就两行：hasNext 比一比游标和长度，next 交出当前元素再前移游标。下半段那个 [Symbol.iterator] 是同一思想在 TS/JS 里的官方形态——语言干脆把迭代器定成了协议，for...of 才能通吃数组、Map、Set 和你自己的集合。

⚖️ 什么时候用，什么时候别用

✅ 适合的场景

  • 想让人遍历，但不想暴露内部结构（下标、指针这些家底不外泄）
  • 同一集合要多种遍历方式，或多个遍历同时进行——各自领导游，游标互不干扰
  • 想给各种集合一个统一的遍历接口：for...of 能通吃数组、Map、Set、自定义集合，靠的就是它

❌ 不适合的场景

  • 自己用的小数组、调用方就一处——直接 for 循环，请导游纯属多余
  • 需要随机访问（直接跳到第 3 个、第 7 个）——迭代器只会一步一步顺着走
  • 遍历过程中要频繁增删元素——游标和结构改动容易打架，多数迭代器直接禁止这么做

⚠️ 容易踩的坑

  • 边遍历边改集合。走到第 3 本时删掉第 2 本，游标当场错位，要么漏元素要么越界。要改就先记下来，遍历完再改。
  • 一个迭代器俩人共用。A 和 B 拿着同一个迭代器轮流 next()，游标是共享的，看到一半发现"怎么少了几本"。各用各的 createIterator()。
  • 不看 hasNext 就 next()。走过头直接抛异常（本例会 throw "已到达集合末尾"）。先问再取，别抢答。
  • 现代语言里重复造轮子。TS/JS 已把迭代器内建成语言协议（Symbol.iterator + for...of），手写 hasNext/next 多半是为了学结构；实际项目优先实现原生协议。

🔗 和其他模式的关系

  • 组合模式常配迭代器：树形的组合结构配一个迭代器，就能把整棵树当平面序列，一层层遍历给外界。
  • 和访问者模式是好搭档：迭代器负责"带路"（挨个取出元素），访问者负责"办事"（对每个元素执行操作）。
  • createIterator() 本质是个工厂方法：聚合对象负责"造出"属于自己的迭代器，造哪种它说了算。
