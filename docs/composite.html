结构型

组合模式 Composite

一句话：把"一个"和"一群"做成同一个模样，用的人不用挑——一把抓，树里哪层都好使。

← 上一个桥接模式 下一个 →装饰器模式

🌰 生活里的例子

公司算工资

老板问 HR："这个月研发部工资总共多少？"HR 不会去挨个数每个员工，而是打电话给各小组长："把你们组的工资总数报给我。"小组长再问手下的每个人。钱一层层往上报，最后加出总数。

注意这里的关键："算工资"这个动作，对单个员工和一个部门来说是同一件事——员工直接报自己的数，部门把下面人的数加起来。老板根本不用管听电话的是一个人还是一个部门。

对应到模式里：员工是"叶子"，部门是"容器"（容器里既能装员工、也能装更小的部门），"报工资总数"就是它们的公共接口。树状层级 + 统一接口，就是组合模式的全部。

😖 没有它会怎样

本仓库的例子是文件系统：统计一个目录的总大小、打印整棵树。如果文件和目录长得不一样，客户端就得处处提防：

直来直去的写法（问题代码）

拿到一个节点先验明正身，再分类处理：

if (node 是文件) { 取 size } → else if (node 是目录) { for 循环孩子，孩子又可能是目录，再套 if…… }

这样写眼下能跑，但麻烦在后头：

  • 嵌套层级一深，if 和 for 就套成洋葱，三层目录三层循环，没人敢维护。
  • 再来一个需求（打印树、统计文件数）就得把这套判断重抄一遍，判断逻辑到处复制。
  • 客户端被迫记住"文件和目录不一样"这个细节，而这个细节本该由数据结构自己消化。

根子上的问题是：文件和目录没长成同一张脸，害得每个用它们的人都要先认脸再动手。

👥 角色构成（这个模式由几块拼成）

角色大白话职责本仓库示例里是谁
组件 Component 统一的脸：定下叶子 和容器 都必须会的动作，大家只认这张脸。 FileSystemNode 接口（getName / getSize / print）
叶子 Leaf 光杆司令：没有下级，问它什么直接给答案。 FileLeaf（一个文件，大小是定死的）
容器 Composite 小组长：揣着一个孩子列表，孩子可以是叶子也可以是另一个容器；问它什么，它就把孩子们问一遍再加起来。 Directory（持有 children 数组）
客户端 拿树人：不管手里是文件还是目录，一句话就出结果。 main()（root.getSize() 一句算总大小）

解耦（把缠在一起的代码拆开，互不认识也能合作）关键在：容器和孩子都实现同一个 FileSystemNode 接口，客户端全程不用 instanceof 区分"单个还是一堆"；"谁装着谁"的知识收进了树自己身上，递归会自动处理任意深度的嵌套。

Directory 的孩子可以是 FileLeaf，也可以是另一个 Directory（src、assets）——树就这样一层层长下去；谁也不认识"整棵树"，只认识自己的孩子。

🔄 运转步骤（跑一遍完整流程）

  1. 定脸：定好 FileSystemNode 接口——getName、getSize、print 三个方法。
  2. 造叶子：FileLeaf 存名字和字节数，问它大小直接报数。
  3. 造容器：Directory 存一个 children 数组，还提供 add() 往里塞孩子。
  4. 建树：srcDir.add(文件)，再 root.add(srcDir)——目录里套目录，想多深有多深。
  5. 一问到底：root.getSize()——根问每个孩子"你多大？"，孩子若是目录就接着问它的孩子，一路递归到叶子，数字层层往上报。
  6. 顺手换招：root.print("") 同样递归，缩进一层层加深，树形结构打印出来了——客户端没写一行判断。

🔍 代码走读

下面是本仓库 TypeScript 实现的骨架（完整版见 ts/composite/main.ts，有删减）：

ts/composite/main.ts（简化）
// 组件接口：文件和目录长同一张脸
interface FileSystemNode {
  getName(): string;
  getSize(): number;
  print(indent: string): void;
}

// 叶子：单个文件，大小直接给
class FileLeaf implements FileSystemNode {
  constructor(
    private readonly name: string,
    private readonly size: number, // 字节
  ) {}
  getSize(): number { return this.size; }
  // getName / print 略
}

// 容器：目录，孩子可以是叶子也可以是另一个目录
class Directory implements FileSystemNode {
  private readonly children: FileSystemNode[] = [];

  add(node: FileSystemNode): this {
    this.children.push(node);
    return this; // 链式 add，方便搭树
  }

  // 递归汇总：目录大小 = 所有孩子大小之和
  getSize(): number {
    return this.children.reduce((sum, child) => sum + child.getSize(), 0);
  }
  // print 同理递归：先打印自己，再让孩子多缩进两格，略
}

// 客户端：不管拿到文件还是目录，同一句话
root.add(new Directory("src").add(new FileLeaf("index.ts", 1200)));
console.log(`项目总大小: ${root.getSize()} B`); // 递归自动算

看懂这段代码，就看懂了整个模式

灵魂就一行：getSize() 里那个 child.getSize()——容器调孩子用的方法和客户端调容器的方法是同一个。自己调自己，树再深也能一层层传到底。

⚖️ 什么时候用，什么时候别用

✅ 适合的场景

  • 数据天生是树形层级：文件系统、UI 控件树、组织架构、菜单子菜单
  • 要对整棵树做递归统计或遍历：算总大小、数节点、整体序列化
  • 希望客户端完全不用区分"拿到的是单个还是一串"，一把梭处理

❌ 不适合的场景

  • 数据压根不是树——硬凑层级纯属自找麻烦
  • 叶子和容器行为差异巨大，硬统一接口后两边都别扭（叶子被迫装哑巴）
  • 对树上不同节点的操作经常新增——那更适合配访问者模式

⚠️ 容易踩的坑

  • 把 add() 塞进公共接口。叶子被迫实现"往文件里塞子文件"这种荒唐方法。本仓库的做法：add 只放在 Directory 上，牺牲一点"完全一致"换安全。
  • 树太深递归爆栈。层级成千上万时递归会栈溢出，得改成用显式栈的循环写法。
  • 删孩子不清引用。节点从逻辑上拿掉了，父亲的 children 里还攥着它，统计和打印就出错。
  • 在容器里对叶子做特判。递归时写"如果是文件就……"——又把接口统一的功劳亲手拆了。

🔗 和其他模式的关系

  • 配迭代器模式最顺：遍历整棵组合树时，用它把递归细节也藏起来，客户端只管 for-of。
  • 配访问者模式：想对树上不同节点干不同的活、又不想污染这些类，访问者负责分发。
  • 和装饰器模式是亲戚：装饰器是"包一个"，组合是"装一群"，都是靠"实现同一接口"让外界无感。
一 句 话 记 住 它 一个和一群长同一张脸：拿树的人不用挑，一层递归传到底。
