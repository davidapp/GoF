行为型

策略模式 Strategy

一句话：同一件事有好几种做法，把每种做法各包成一个对象，用哪套随时换、随换随生效。

← 上一个状态模式 下一个 →模板方法模式

🌰 生活里的例子

导航 App 选出行方式

同样从家到公司，导航 App 底下有几个图标：驾车、公交、步行。点哪个，它就用哪套算法给你算路线——驾车走高架，公交挑换乘少的，步行专钻小胡同。

注意一个细节：你的起点终点一直没变，变的只是"用哪套算法"。而且你半路改主意，从驾车切到公交，App 不用重启、不用重填地址，换一套算法重新算就是了。

对应到模式里：导航 App 是"上下文"，"算路线"这个约定是策略接口，驾车 / 公交 / 步行三套算法是三个具体策略，你点图标就是 setStrategy() 换人。目的地（数据）不动，算法随便换。

😖 没有它会怎样

本仓库的例子是购物车结账：同一笔钱，可以用信用卡、PayPal、加密货币三种方式付。最直接的写法：在结账方法里挂一串 if-else。

直来直去的写法（问题代码）

结账时挨个问支付类型：

if (payType === "creditCard") { 卡号打码、拼信用卡话术 }
else if (payType === "paypal") { 拼账户邮箱话术 }
else if (payType === "crypto") { 算汇率、折算 USDT } ……

眼下能跑，越往后越难受：

  • 购物车被迫懂每种支付的门道：卡号怎么打码、汇率怎么折算，全写在结账方法里，方法越长越胖。
  • 加一种支付就要动一次结账代码：新接一个"银行转账"，又得往 if 链里插一段，改坏了影响所有支付方式。
  • 支付逻辑没法单独测试和复用：想单测信用卡那段？对不起，它长在购物车身上，抠都抠不出来。

根子上的问题：购物车不该懂"怎么付钱"，它只该懂"把钱交给会付的人"。把每种付法各包成一个对象，问题就消失了。

👥 角色构成（这个模式由几块拼成）

角色大白话职责本仓库示例里是谁
策略接口 Strategy 一份合同：只约定"会收钱"这一件事（pay(amount)），不管你具体怎么收。 PaymentStrategy 接口
具体策略 各种干活的手艺人：信用卡有信用卡的收法，PayPal 有 PayPal 的收法，互相不认识也不打扰。 CreditCardStrategy、PayPalStrategy、CryptoStrategy
上下文 Context 用人单位：手里攥着当前策略，活儿来了转手外包出去，还能随时换人。 ShoppingCart

解耦（把缠在一起的代码拆开，互不认识也能合作）的关键：购物车只认识"策略接口"，不认识任何一种具体支付。所以加第四种支付方式，购物车一行代码都不用改——只要新来的会 pay()，就能上岗。

🗺️ 结构图（谁认识谁、谁调用谁）

箭头方向 = 调用方向：购物车只调用策略接口；换支付方式 = setStrategy() 把手里的引用换个对象，别的一概不动。

🔄 运转步骤（跑一遍完整流程）

  1. 装货：cart.addItem("机械键盘", 399)、addItem("鼠标", 199)，商品进了购物车。
  2. 挑做法：创建 new ShoppingCart(new CreditCardStrategy("4111...", "123"))——一开始用信用卡结账。
  3. 结账：cart.checkout() 把商品加出总价 598，转手交给当前策略：this.strategy.pay(598)，信用卡策略打印支付信息。
  4. 换人：cart.setStrategy(new PayPalStrategy("buyer@example.com"))——购物车只是把 strategy 引用换了个对象。
  5. 再结账：同一辆车、同一批货、同一个 checkout 方法，这次 PayPal 策略出面，输出另一种支付话术；再切加密货币还能算汇率折 USDT。
  6. 回头看：从头到尾 ShoppingCart 里没有一个判断支付类型的 if。

🔍 代码走读

下面是本仓库 TypeScript 实现的骨架（完整版见 ts/strategy/main.ts，有删减）：

ts/strategy/main.ts（简化）
// 策略接口：只约定"会收钱"这一件事
interface PaymentStrategy {
  readonly name: string;
  pay(amount: number): string;
}

// 具体策略：每种支付方式各管各的，互相不认识
class CreditCardStrategy implements PaymentStrategy {
  readonly name = "信用卡";

  constructor(private readonly cardNumber: string, private readonly cvv: string) {}

  pay(amount: number): string {          // 信用卡的收法：卡号打码
    const masked = this.cardNumber.slice(-4).padStart(this.cardNumber.length, "*");
    return `使用信用卡(${masked}) 支付 ¥${amount.toFixed(2)}`;
  }
}

// 上下文：只管算总价，收钱的事全外包
class ShoppingCart {
  constructor(private strategy: PaymentStrategy) {}

  setStrategy(strategy: PaymentStrategy): void {  // ② 运行时换做法
    this.strategy = strategy;
  }

  checkout(): void {
    const total = 598;
    console.log(this.strategy.pay(total));         // ① 委托给当前策略
  }
}

看懂这段代码，就看懂了整个模式

核心就一行：this.strategy.pay(total)——上下文把活儿连同数据一起递给当前策略。三种支付三套实现互不知晓，换人只是一个赋值，if-else 从此绝迹。

⚖️ 什么时候用，什么时候别用

✅ 适合的场景

  • 同一件事确实有多套可互换的算法：支付、排序、压缩、路线规划、折扣计算
  • 需要在运行时换做法，而不是写死在代码里
  • if-else 的每个分支都是一整套逻辑，方法已经开始发胖

❌ 不适合的场景

  • 几个算法就差一两行——抽成一堆类，读代码的人反而要追好几个文件
  • 算法编译期就定死、永远不会换——直接写函数调用更直白
  • 调用方被迫搞清每个策略的区别才能选对——细节泄漏了，不如再配个工厂

⚠️ 容易踩的坑

  • 策略越加越多没人管 → 类爆炸。一堆只差个参数的策略类（打八折、打九折、打九五折……），不如合并成一个带参数的策略。
  • 上下文和策略偷偷共享可变状态 → 换人时残留脏数据。策略应该是"给你数据、你还我结果"，各自不留后手，否则换策略后出的 bug 极难查。
  • 策略接口越定越肥 → 每加一个方法全体现有策略都得改。接口只留"做这件事"的最小约定（本仓库就一个 pay()），别把各种边角需求都塞进来。
  • 和状态模式傻傻分不清 → 用错场合。记住：策略之间互不认识、由你挑；状态之间互相认识、自己接力流转。分不清就回到"谁决定切换"这一问。

🔗 和其他模式的关系

  • 和状态模式结构几乎是双胞胎，差别在意图：策略是你主动挑一把工具（换不换你说了算），状态是当前状态推着你走（换班由状态自己接力）。
  • 策略对象常用工厂方法模式来造：调用方说"给我信用卡策略"，连 new 都不用自己写。
  • 和命令模式都爱"把一段逻辑包成对象"：策略包的是"一种做法"，重在替换；命令包的是"一次请求"，重在排队、撤销、记录。
一 句 话 记 住 它 一件事多种做法，车不动，引擎随便换。
