状态模式 State

一句话：同一个操作，落在不同状态下反应不同——把每种状态做成一个小对象，谁当班谁说了算。

← 上一个观察者模式 下一个 →策略模式

🌰 生活里的例子

手机的响铃 / 静音 / 勿扰模式

同一通电话打进来，响铃模式下手机大声唱歌，静音模式下只轻轻震动，勿扰模式下屏幕亮一下就没下文了。来电还是那通来电，反应却完全不同——区别不在电话，在手机此刻处于哪种模式。

而且你切换模式时，手机不用拆开重组：它只是把"处理来电"这件事交给当前在班的那个模式对象。你按音量键选模式，相当于告诉手机：下一位，你来值班。

对应到模式里：手机是"上下文"，三种模式是三个"具体状态"，来电是那个同样的操作。上下文自己不动脑，把操作原样转给当班的状态；干完活，状态自己决定下一班交给谁。

😖 没有它会怎样

本仓库的例子是一个音频播放器 AudioPlayer，有播放中 / 已暂停 / 已停止三种状态，play() / pause() / stop() 三个操作。最直接的写法：每个方法开头都问一遍"我现在是什么状态"。

直来直去的写法（问题代码）

每个方法里都挂一串 if-else：

if (state === "playing") { 暂停播放; state = "paused"; }
else if (state === "paused") { 已经处于暂停状态; }
else if (state === "stopped") { 已停止，无法暂停; } ……

三个操作 × 三种状态 = 九个分支，眼下写得出来，后头要人命：

  • 巨型 if-else 满天飞：每个方法都要把所有状态从头问一遍，重复的判断抄三份。
  • 加一种状态，全城开挖：想加个"快进中"？三个方法里的 if-else 链一个都不能漏，漏一处就出诡异 bug。
  • 看不出状态怎么流转：散在各分支里的字符串赋值，谁也说不清"从哪能到哪"，改起来全靠胆子。

根子上的问题："状态"和"该状态下的行为"被硬拆在两处。把它们绑在一起、一种状态一个类，问题就消失了。

👥 角色构成（这个模式由几块拼成）

角色大白话职责本仓库示例里是谁
上下文 Context 对外的那张脸：持有"当前状态"，收到操作就原样转给当前状态。自己一行判断都不写。 AudioPlayer
状态接口 State 值班守则：约定每种状态都要会处理 play / pause / stop 三件事。 PlayerState 接口
具体状态 真正的值班员：只回答"我这种状态下，这个操作怎么办"，并决定下一个接班的是谁。 PlayingState、PausedState、StoppedState

解耦（把缠在一起的代码拆开，互不认识也能合作）的关键：转换规则收进了状态类内部。"暂停时该切到已暂停"这条规矩写在 PlayingState 自己家里，别处一概不知——加新状态不用碰任何旧代码。

🔄 运转步骤（跑一遍完整流程）

  1. 开机：new AudioPlayer()，内部 state 初始为 StoppedState（已停止）。
  2. 按播放：player.play() 转手调 this.state.play(this)——接电话的是 StoppedState，它打印"从头开始播放"，并回手 player.setState(new PlayingState())。
  3. 按暂停：这次接电话的换成 PlayingState，它打印"暂停播放"，把班交给 PausedState。
  4. 再按暂停：PausedState 在班上，只回一句"已经处于暂停状态"，什么都不换。
  5. 继续玩：播放、停止轮流来，每次都是"当前在班的状态"说了算，同样的按键走出不同的结果。
  6. 回头看：从头到尾 AudioPlayer 里没有出现一个 if (state === ...)。

🔍 代码走读

下面是本仓库 TypeScript 实现的骨架（完整版见 ts/state/main.ts，有删减）：

ts/state/main.ts（简化）
// 状态接口：约定每种状态都要会处理的三件事
interface PlayerState {
  readonly name: string;
  play(player: AudioPlayer): void;
  pause(player: AudioPlayer): void;
  stop(player: AudioPlayer): void;
}

// 具体状态：只管"我这种状态下"该怎么反应
class PlayingState implements PlayerState {
  readonly name = "播放中";

  pause(player: AudioPlayer): void {
    console.log("暂停播放");
    player.setState(new PausedState());  // 状态自己决定下一个状态
  }
  // play / stop 同理，此处省略
}

// 上下文：一个纯传话筒，没有任何 if-else
class AudioPlayer {
  private state: PlayerState = new StoppedState();

  setState(state: PlayerState): void {   // 状态回手换班的唯一入口
    this.state = state;
  }

  pause(): void { this.state.pause(this); }  // 谁在班上谁处理
}

看懂这段代码，就看懂了整个模式

核心就两下：上下文把操作连同自己一起递给当前状态（this.state.pause(this)），状态干完活回手 setState() 换班。九个 if 分支变成三个各司其职的小类，转换规矩再也不会散落一地。

⚖️ 什么时候用，什么时候别用

✅ 适合的场景

  • 一个对象有几个明确的状态，同一操作在不同状态下反应不同（播放器、订单流转、审批单）
  • 代码里已经长出判断状态的巨型 if-else / switch
  • 想把"状态之间怎么流转"的规则收拢到一处，显式写清楚

❌ 不适合的场景

  • 就两三个状态、行为差异很小——一个布尔判断更省事
  • 状态基本不切换，或者每种状态下行为都一样——硬上状态类是脱裤子放屁
  • 状态要掏上下文一大堆内部数据——可能拆错了单元，先回头想想怎么分

⚠️ 容易踩的坑

  • 状态类互相 new 成瘾 → 耦成一团。像本仓库这样状态类自己没有字段，全程序共用一个实例就够了（甚至做成单例），不必每次换班都 new。
  • 把转换规则全塞回上下文 → 模式退化成换皮 if-else。setState 的调用权应该交给状态类，上下文一旦开始判断"接下来该是谁"，就白重构了。
  • 状态对象里偷偷存数据 → 换班时数据错乱。状态类应该是"无状态"的（只描述行为不存业务数据），本仓库三个状态类就一个字段都没有。
  • 非法操作被默默吞掉。已停止时按暂停，StoppedState 明确回一句"已停止，无法暂停"——该拒绝就明说，装聋作哑的 bug 最难查。

🔗 和其他模式的关系

  • 和策略模式是结构上的双胞胎，差别在意图：策略是你主动挑一把工具（换不换你说了算），状态是当前状态推着你走（换班由状态自己接力）。
  • "状态变了"常常要广播给界面刷新，正好接上观察者模式：状态一切换，订阅者自动收到通知。
  • 无字段的状态类全程序只需一份，可以配合单例模式共享实例，省掉反复创建。
一 句 话 记 住 它 谁在班上谁接电话——同一个按键，换个状态就是换种反应。
