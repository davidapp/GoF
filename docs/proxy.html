代理模式 Proxy

一句话：派个替身挡在真家伙前面：该拦的拦、该缓的缓，正主最后才登场。

← 上一个享元模式 下一个 →责任链模式

🌰 生活里的例子

明星的经纪人

想请明星商演，你不能直接冲到明星本人跟前谈。先过经纪人这一关：他先看你资质（权限校验）、查明星档期（控制访问）、谈不拢直接把你的邀约挡回去；谈拢了，才安排明星本人登台。

注意两个细节：对外谈的都叫"商演"，流程一样——你从头到尾面对的都是经纪人，甚至感觉不到明星什么时候进的场；经纪人自己不唱歌，他只管"放不放行、何时放行"，唱还是明星唱。

对应到模式里：经纪人是代理，明星是真实对象，"商演流程"是两人共同的接口。替身控制访问的时机和资格，正主只管干正事。

😖 没有它会怎样

本仓库的例子是相册应用：相册里躺着一堆图片，RealImage 一构造就会真的去读磁盘（高开销操作）。如果不用代理，打开相册就：

直来直去的写法（问题代码）

一上来就把真家伙全造出来：

const gallery = [new RealImage("p1.jpg"), new RealImage("p2.jpg"), …… new RealImage("p100.jpg")] —— 100 次磁盘 I/O 在这一行全部发生。

这样写眼下能跑，但麻烦在后头：

  • 用户可能只看第一张，剩下 99 张的加载全是白等，启动慢得像爬。
  • 100 张图的内存全部占住，哪怕用户压根没往下翻。
  • 想在加载前后加缓存、加权限、加日志？只能改 RealImage 本尊或改所有调用方，两处都是雷区。

根子上的问题是："又贵又不一定用"的东西不该急着造，中间缺一个替你把关、垫后的人。

👥 角色构成（这个模式由几块拼成）

角色大白话职责本仓库示例里是谁
抽象主题 Subject 共同身份：定下"是张图片就得会 display()"——代理和真家伙都长这张脸，才能互相顶替。 Image 接口
真实主题 正主：干重活的那位——构造函数里就真的去读磁盘。 RealImage（构造即 loadFromDisk()）
代理 Proxy 替身：构造零成本，揣着文件名按兵不动；第一次 display() 才请出正主并记住，之后直接转发。 ImageProxy（懒加载 + 缓存）
客户端 看相册的人：手里攥着 Image[]，不知道也不关心里面装的是替身还是正主。 gallery: Image[]

解耦（把缠在一起的代码拆开，互不认识也能合作）关键在：代理和真实对象实现同一个 Image 接口，所以"懒加载、缓存、权限"这些附加逻辑塞进代理后，客户端一行代码都不用改——它以为自己在调图片，其实在跟经纪人说话。

箭头方向 = 调用方向：只有代理调真实对象；真实对象从不回头找代理。两者都实现 Image，所以在客户端眼里可以无感互换。

🔄 运转步骤（跑一遍完整流程）

  1. 建相册：gallery 里放三个 new ImageProxy("photoN.jpg")——注意，此刻零磁盘 I/O，替身只揣了个文件名。
  2. 首次查看：用户翻到第一张，调 gallery[0].display()，请求先落在代理手里。
  3. 请正主：代理一看 realImage 还是空的——new RealImage(filename)，这一刻磁盘才真正转起来。
  4. 转发：代理接着调 realImage.display()，图片显示，用户毫无察觉。
  5. 再看白拿：用户翻回第一张再看，代理发现正主已就位，直接转发，不再加载。
  6. 换图再走一遍：翻到 photo2，首次访问，代理再请一次正主——每张图都只在自己被看时才花这份钱。

🔍 代码走读

下面是本仓库 TypeScript 实现的骨架（完整版见 ts/proxy/main.ts，有删减）：

ts/proxy/main.ts（简化）
// 抽象主题：代理和真家伙的共同身份
interface Image {
  display(): void;
}

// 真实主题：一构造就真的去读磁盘（贵！）
class RealImage implements Image {
  constructor(private readonly filename: string) {
    this.loadFromDisk(); // 磁盘 I/O 发生在构造这一刻
  }
  private loadFromDisk(): void {
    console.log(`  [磁盘 I/O] 正在从磁盘加载图片: ${this.filename}`);
  }
  display(): void { console.log(`显示图片: ${this.filename}`); }
}

// 代理：构造时啥也不干，第一次 display 才请出正主
class ImageProxy implements Image {
  private realImage: RealImage | undefined; // 缓存正主

  constructor(private readonly filename: string) {}

  display(): void {
    if (this.realImage === undefined) {
      this.realImage = new RealImage(this.filename); // 首次：真正加载
    }
    this.realImage.display(); // 之后：直接转发
  }
}

// 客户端：gallery 里全是代理，创建时零磁盘 I/O
const gallery: Image[] = [
  new ImageProxy("photo1.jpg"),
  new ImageProxy("photo2.jpg"),
];
gallery[0]?.display(); // 这一刻，photo1 才真正加载

看懂这段代码，就看懂了整个模式

核心就一个 if："正主在场吗？不在才请，在就直接用"。把创建的时机从"构造时"拖到"第一次真正使用时"，懒加载、缓存这些附加控制就全藏在这个 if 里了。

⚖️ 什么时候用，什么时候别用

✅ 适合的场景

  • 对象创建很贵（读盘、拉网络、大量计算），而且不一定每次都用——懒加载最划算
  • 要控制访问资格：没登录不给看、没权限不给调
  • 想加缓存、日志、计数这些附加逻辑，又不想动原类和调用方

❌ 不适合的场景

  • 对象创建很便宜——套层代理纯属多过一道手，还添乱
  • 马上就要用真实对象的完整状态，"延迟"毫无意义
  • 附加逻辑复杂到喧宾夺主（一堆鉴权+重试+限流）——那该是独立的服务层，不是替身

⚠️ 容易踩的坑

  • 代理和正主状态不同步。正主在别处被改了、甚至释放了，代理还攥着旧引用傻乐——共享同一份生命周期管理很关键。
  • 代理里塞太多逻辑。鉴权、缓存、重试、日志全堆进 display()，出问题时排查两眼一黑——替身该薄，厚了就是设计坏了。
  • 缓存形同虚设。缓存的 key 选错（比如按"文件名+时间戳"），或者压根没缓存住正主，每次访问都穿透，代理就成了纯过路费。
  • 忘了处理正主的失败。懒加载那一瞬间才暴露真实错误（文件不存在、网络超时），客户端没准备好的话，bug 会在"第一次调用"时才炸出来。

🔗 和其他模式的关系

  • 和装饰器模式是结构双胞胎：都是"同接口 + 持引用 + 转发"。区别在意图——代理管"能不能访问、何时访问"，通常一层，客户端不知情；装饰器管"往上叠加职责"，可以多层，客户端主动去拼。
  • 和适配器模式都包一层：代理不换接口，只控制访问；适配器专门改接口的形状。
  • 和外观模式都算"中间人"：代理是替身，一对一顶替；外观是总开关，一对多简化。
