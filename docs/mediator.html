中介者模式 Mediator

一句话：一群对象要互相聊天，谁也不直接找谁，统统通过一个"群主"转话；谁进群谁退群，别人根本不用知道。

🌰 生活里的例子

机场塔台

天上几十架飞机要降落、要避让、要排队进跑道，但它们从不互相直接通话——你想想，50 架飞机两两喊话，频道里得乱成什么样。真实做法是：每架飞机只跟塔台说话，"我要降落"；塔台看着全局大屏，安排谁先谁后、通知谁绕一圈再进。

两个细节：飞机之间谁也不认识谁；一架新飞机进场，只要跟塔台打个招呼就融入了编排，其他飞机毫无感知。

这个比喻对应模式里的什么：塔台 = 中介者（ChatRoom，拿着全员名单、定所有转达规则）；飞机 = 同事类（User，互不认识）；飞机无线电里只存塔台一个频道 = 同事对象只持有一个中介者引用；塔台安排谁先谁后 = 交互规则全部集中在中介者一处。

😖 没有它会怎样

本仓库的场景是聊天室：Alice、Bob、Carol 互发消息。最直接的写法是每个人手里都攥着其他所有人的引用，发消息时挨个点名：

直来直去的写法（问题代码）

Alice 发消息时直接调用其他人：

bob.receive(msg) → carol.receive(msg) …… Alice 的"通讯录"里得有所有人。

这样写眼下能跑，但麻烦在后头：

  • 新人进群，全体老用户改代码。来了个 Dave？Alice、Bob、Carol 都得把 Dave 加进自己的通讯录——一处不改他就收不到消息。
  • 引用缠成蜘蛛网。N 个人两两互持引用是 N×(N-1) 条线，10 个人就是 90 条，画出来没法看，谁也不敢动。
  • 转发规则散落各处。"不给发送者本人发、要屏蔽黑名单……"这些规则写在每个用户自己的代码里，改一条规则要改 N 处。

根子上的问题是多对多的两两直连把所有人焊死在一起。拆开的办法：把"认识所有人"这件事交给一个人——群主。

👥 角色构成（这个模式由几块拼成）

角色大白话职责本仓库示例里是谁
抽象中介者 定规矩："群主要有注册和转话两个本事"。 ChatMediator 接口
具体中介者 群主本体。拿着全员名单，收到一条消息就转发给除发送者外的所有人。 ChatRoom 类
同事类 Colleague 群成员。通讯录里只存群主一个联系方式：说话交给他转，听话等他送。 User 类（Alice、Bob、Carol）
客户端 建群、拉人，之后基本不掺和。 main() 函数

解耦关键在哪：用户之间零引用，每人只认识群主。多对多的蜘蛛网被压成"众星捧月"的星型：N 个人只有 N 条线，全都连向中介者。新人入群只需 new User(name, chatRoom)（构造时自动 register），任何老用户一行代码不用改——这就是解耦（把缠在一起的代码拆开，互不认识也能合作）。

没有群主时：3 个人两两直连要 6 条线，10 个人就是 90 条。有了群主：每人只 1 条线，用户之间谁也不认识谁；想改"谁能收到什么"的规则，只改群主一处。

🔄 运转步骤（跑一遍完整流程）

  1. 建群：客户端 new ChatRoom()，一个群主就位，名单还是空的。
  2. 入群：new User("Alice", chatRoom)——构造函数里自动调 mediator.register(this)，群主把 Alice 记进名单。Bob、Carol 同理。
  3. 发言：Alice 调 send("大家好")，自己不点名任何人，直接把消息交给 chatRoom.sendMessage()。
  4. 转达：群主遍历名单，跳过发送者 Alice 本人，挨个调 bob.receive(...)、carol.receive(...)。
  5. 回应：Bob 也发言，同样只找群主，消息被转给 Alice 和 Carol——一来一回，用户之间零接触。
  6. 扩容：再 new User("Dave", chatRoom)，Dave 立刻能收发消息，Alice 们毫无感知、零改动。

🔍 代码走读

下面是本仓库 TypeScript 实现的骨架（完整版见 ts/mediator/main.ts，有删减）：

ts/mediator/main.ts（简化）
// 具体中介者：拿着全员名单，负责转发
class ChatRoom implements ChatMediator {
  private readonly users: User[] = [];

  register(user: User): void {          // 入群：记进名单
    this.users.push(user);
  }

  sendMessage(message: string, sender: User): void {
    for (const user of this.users) {
      if (user !== sender) {            // 除了说话的人，挨个转达
        user.receive(message, sender.getName());
      }
    }
  }
}

// 同事类：通讯录里只有群主，不认识任何其他用户
class User {
  constructor(
    private readonly name: string,
    private readonly mediator: ChatMediator,
  ) {
    this.mediator.register(this);       // 生下来就进群
  }

  send(message: string): void {
    console.log(`[${this.name} 发送]: ${message}`);
    this.mediator.sendMessage(message, this);  // 交给群主转发
  }

  receive(message: string, from: string): void {
    console.log(`  -> ${this.name} 收到来自「${from}」的消息: ${message}`);
  }
}

看懂这段代码，就看懂了整个模式

核心就两处：User 的 send() 只调群主、不点名任何人；ChatRoom 的 sendMessage() 遍历名单、跳过发送者。把"发给谁、怎么发"的规则全部收进群主一处，成员就彻底解放了。

⚖️ 什么时候用，什么时候别用

✅ 适合的场景

  • 一组对象互相引用已经织成蜘蛛网（N×(N-1) 条线），改一个牵一串
  • 想把交互规则集中管理：谁能跟谁说话、消息怎么路由，改一处全局生效
  • 对象想单独复用，却被一堆"熟人"缠着抽不出来

❌ 不适合的场景

  • 交互本来就简单、就两三个对象——加个中介者纯属多一层转手
  • 交互是单向广播（一个变了通知大家）——用观察者更轻，别上中介者
  • 协调逻辑本身巨复杂——硬塞进一个类会养成"上帝对象"，该考虑拆分或分区

⚠️ 容易踩的坑

  • 中介者养成"上帝对象"。谁跟谁说话、消息过滤、权限、日志全往 ChatRoom 里堆，最后这个类几千行，谁也不敢动。群主只管"路由"，别管业务加工。
  • 同事类反向翻群主的家底。User 开始遍历 ChatRoom 的名单、自己动手挑收件人——解耦成果瞬间归零。同事只准调中介者的公开接口。
  • 和观察者傻傻分不清。观察者是"一个喇叭，单向广播给所有订阅者"；中介者是"一群人对聊，全经群主转话，群主还能定规矩"。方向和用途都不一样，别选错。
  • 中介者成了单点瓶颈。所有消息都过它，它一卡全场哑；规则一错全局错。测试和监控要重点照顾它。

🔗 和其他模式的关系

  • 和观察者模式最容易混，一句话分清：观察者是"单向广播"——一个主题变了，通知所有订阅它的人，订阅者不回话；中介者是"多向协调"——大家你一言我一语，全经群主转话，群主还能定规矩。聊天室若只需要"管理员发公告"，用观察者就够了。
  • 和外观模式都在"收拢复杂度"，但方向相反：外观是单向的——替你简化"进去调用"的入口；中介者是双向的——内部一群对象互相说话都得靠它协调。
  • 中介者常被做成单例：全局只有一个聊天室/事件总线，大家进来找的都是同一个群主。
一 句 话 记 住 它 别再两两打电话了，都进群找群主；谁进群谁退群，其他人根本不用知道。
