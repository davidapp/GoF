原型模式 Prototype

一句话：不从零造，直接复印一份现成的，改两笔就是新的。

← 上一个工厂方法模式 下一个 →单例模式

🌰 生活里的例子

复印一份排好版的申请表

你花了一下午把申请表排版调到完美：字体、字号、页边距全弄妥了。现在要交给 10 个部门，每个部门还都要求小改：这家要填手机号，那家要换日期。你绝不会重新排版 10 遍，而是复印 10 份，在复印件上各自涂改——原件永远干干净净。

如果这 10 个部门明年还要同样的表？把原件塞进文件柜贴个标签，随取随复印。

对应到模式里：原件就是原型对象（一个调好属性的 Circle），复印就是 clone()，复印件上随便改（克隆体和原件互不影响），文件柜就是原型注册表（按名字存模板的 Map）。

😖 没有它会怎样

本仓库的示例是图形编辑器：画布上要生成一堆相似的图形，比如 20 个"红色、半径 5 的圆"，只是位置各不相同。最直接的写法是每次都从头 new：

直来直去的写法（问题代码）

new Circle("红色", 10, 20, 5)

new Circle("红色", 30, 40, 5)

new Circle("红色", 50, 60, 5) ……

参数一个个重填。更狠的情况：这个对象是查了三张数据库表、读了个大文件才拼出来的，难道每次都重来一遍？

这样写的麻烦：

  • 重复劳动：模板属性要一遍遍抄，抄漏一个参数不报错，直接埋 bug。
  • 构造成本高的对象反复构造：查库、读文件、调接口的活儿每次重干，性能白白烧掉。
  • 想要"和那个一模一样、只改一点"的副本：手动重填等于逼你把人家的内部字段全看一遍，费劲还容易错。

根子上的问题是把"造新对象"等同于"从零开始"——明明旁边就有一份现成的，复印比重做快多了。

👥 角色构成（这个模式由几块拼成）

角色大白话职责本仓库示例里是谁
原型接口 Prototype 一句合同："会自己复印自己。" Prototype<T> 接口（clone()）
抽象原型 把公共字段（颜色、坐标）放这里，搭好克隆的架子。 Shape 抽象类
具体原型 自己最懂自己有哪些字段，new 一个同类对象、逐个抄进去。 Circle、Rectangle
原型注册表 按名字保管一批"标准原件"的文件柜，要货时直接复印。 registry（Map<string, Shape>）

解耦关键：客户端想要新对象，只要手里有一个现成的，调 clone() 就行——不需要知道它的类叫什么、不需要调用它的构造函数。配上注册表，甚至用字符串名字就能拿到模板复印。

箭头方向 = 调用方向：谁想要副本谁调 clone()；注册表只是替你保管原件的柜子，柜里每份原型都能无限次复印。

🔄 运转步骤（跑一遍完整流程）

  1. 造原件：精心 new Circle("红色", 10, 20, 5)，把属性都调到满意。
  2. 复印：original.clone() 返回一个全新的 Circle，字段和原件一模一样。
  3. 验明正身：original === cloned 结果是 false——两个对象，内存里各占各的。
  4. 改副本：把克隆体的 x 改成 100、颜色改成"蓝色"，回头看原件纹丝不动。
  5. 存柜：把常用模板放进注册表，比如 ["small-circle", new Circle("黑色", 0, 0, 1)]。
  6. 批量取：要货时 registry.get("small-circle").clone()，随取随复印，取多少份互不干扰。

🔍 代码走读

下面是本仓库 TypeScript 实现的骨架（完整版见 ts/prototype/main.ts，有删减）：

ts/prototype/main.ts（简化）
// 原型接口：会克隆自己的对象
interface Prototype<T> {
  clone(): T;
}

// 抽象原型：公共字段 + 抽象 clone
abstract class Shape implements Prototype<Shape> {
  constructor(public color: string, public x: number, public y: number) {}
  abstract clone(): Shape;
}

// 具体原型：new 一个同类对象，逐字段抄进去
class Circle extends Shape {
  constructor(color: string, x: number, y: number, public radius: number) {
    super(color, x, y);
  }
  clone(): Circle {
    return new Circle(this.color, this.x, this.y, this.radius);
  }
}

// 用法：改克隆体，原型毫发无损
const original = new Circle("红色", 10, 20, 5);
const cloned = original.clone();
cloned.x = 100;         // 只改克隆体
cloned.color = "蓝色";
original === cloned;    // false —— 两个不同的实例

// 原型注册表：按名字存模板，要时直接复印
const registry = new Map<string, Shape>([
  ["small-circle", new Circle("黑色", 0, 0, 1)],
  ["big-rect", new Rectangle("白色", 0, 0, 100, 50)],
]);
const copy = registry.get("small-circle")!.clone();

看懂这段代码，就看懂了整个模式

clone() 的套路就一句话：new 一个同类的对象，把自己每个字段抄进去。本例字段全是数字和字符串（值类型），抄值就够；字段里有对象、数组时得考虑深拷贝（连引用的东西也一起复印），否则踩共享坑。

⚖️ 什么时候用，什么时候别用

✅ 适合的场景

  • 对象构造成本高（查库、读文件、复杂计算），复制比重建划算得多
  • 要批量生成"相似但各自微调"的对象（图形、怪物、配置副本）
  • 运行时按名字/配置动态决定用哪种对象，且种类不多

❌ 不适合的场景

  • 对象就几个值字段、构造便宜——直接 new，克隆反而多此一举
  • 字段大量是引用类型、嵌套深——深拷贝又贵又容易写错
  • 每个新对象都必须走完整构造逻辑（初始化、注册、校验）——clone 会绕过构造函数

⚠️ 容易踩的坑

  • 浅拷贝的共享坑。字段里有数组或对象时，默认只抄"地址"，克隆体和原件共用同一份内部数据，改一个动两个，bug 藏得极深。
  • 漏抄新字段。类里新加字段忘了同步改 clone()，克隆出来的对象缺胳膊少腿，编译器还不报错。
  • 绕过构造函数。clone 不走 constructor，构造函数里的副作用（计数、日志、注册监听）统统不会执行，行为悄悄变了样。
  • 循环引用。对象互相指着对方时深拷贝容易死循环，得专门处理"抄过了就不再抄"。

🔗 和其他模式的关系

  • 常与工厂方法模式合体：工厂里存一份原型，create() 时返回 clone() 而不是 new，省掉重复构造。
  • 和单例模式是两个极端：单例全程序只此一份、严禁复制；原型是使劲复制，副本越多越好。
  • "复印一份留底、以后恢复原样"这个动作，正是备忘录模式的核心玩法，两者思路同源。
