适配器模式 Adapter

一句话：插头对不上插座？别改电器也别改墙，中间垫一个"转换头"，两边立刻都好使。

← 上一个单例模式 下一个 →桥接模式

🌰 生活里的例子

出国旅行的电源转换头

你带着国标插头的吹风机去欧洲旅行，酒店的插座是欧标的——插头插不进去。怎么办？吹风机不能拆，墙更不能砸，你花十块钱买一个转换头：一头是欧标插脚，另一头是国标插孔，往中间一接，通电了。

注意这个转换头自己不发电也不耗电，它只干一件事：让两边各认各的标准，中间替它们"翻译"。

对应到代码里：你的电器就是客户端（只认识国标插孔），欧洲的墙就是第三方类（只提供欧标插脚），转换头就是适配器。谁也不用改，接上就能用。

😖 没有它会怎样

本仓库的例子是支付：应用里统一的接口是 PaymentProcessor.pay(yuan)，单位是"元"。现在要接入第三方 Stripe，可人家的 SDK 只提供 chargeInCents(cents)，方法名不一样，单位还是"分"。最直接的写法：

直来直去的写法（问题代码）

在每个付款的地方都写一段特判：

if (用的是 Stripe) { 乘 100、四舍五入、调 chargeInCents } else { 直接调 pay } ……

这样写眼下能跑，但麻烦在后头：

  • 每接一家新支付渠道，付款代码就得再开一次膛。下个月来个 PayPal？再抄一段 if。
  • "元变分"这种换算胶水洒得满地都是，十处调用抄十遍，改一处漏九处。
  • 付款流程被迫认识每家第三方的细节，第三方 SDK 一升级，你的业务代码跟着抖三抖。

根子上的问题是：不该让客户端去迁就别人，该在中间放一个专门翻译的东西。

👥 角色构成（这个模式由几块拼成）

角色大白话职责本仓库示例里是谁
目标接口 Target 你想要的那个插座孔型：全应用统一的标准，大家只认它。 PaymentProcessor 接口（pay(yuan)）
被适配者 Adaptee 那个接口对不上的家伙，通常是第三方库或老代码，动不得。 StripePayment（只提供 chargeInCents(cents)）
适配器 Adapter 转换头本体：实现目标接口，怀里揣着被适配者，负责翻译转手。 StripeAdapter
对照组 天生就符合标准接口的类，说明适配器只为"对不上"的家伙服务。 AlipayPayment（原生实现 PaymentProcessor）

解耦（把缠在一起的代码拆开，互不认识也能合作）关键在：客户端只认 PaymentProcessor 这张"孔型图"，根本不知道背后是支付宝还是被包了一层的 Stripe；而"元乘一百变分"这种脏活，全关在 StripeAdapter 一个屋里，半点不外漏。

🔄 运转步骤（跑一遍完整流程）

  1. 定标准：应用统一定好 PaymentProcessor 接口，金额单位用"元"。
  2. 引第三方：接入 StripePayment，发现方法名和单位都对不上。
  3. 造转换头：写 StripeAdapter，实现 PaymentProcessor，构造时收下一个 StripePayment。
  4. 翻译：客户调 pay(128.5)，适配器把元乘 100 四舍五入成 12850 分，转手调 chargeInCents(12850)。
  5. 无缝接入：checkout(stripeAdapter, 128.5)，用起来跟支付宝一模一样。
  6. 继续扩展：以后再接 PayPal，新写一个 PayPalAdapter 就行，付款代码一行不改。

🔍 代码走读

下面是本仓库 TypeScript 实现的骨架（完整版见 ts/adapter/main.ts，有删减）：

ts/adapter/main.ts（简化）
// 第三方 SDK（被适配者）：只认"分"，接口和单位都对不上
class StripePayment {
  chargeInCents(amountInCents: number): string {
    return `Stripe 扣款成功：${amountInCents} 分`;
  }
}

// 目标接口：应用统一的支付接口，单位是"元"
interface PaymentProcessor {
  pay(yuan: number): string;
}

// 适配器：实现目标接口，怀里揣着第三方实例，负责翻译
class StripeAdapter implements PaymentProcessor {
  constructor(private readonly stripe: StripePayment) {}

  pay(yuan: number): string {
    const cents = Math.round(yuan * 100);    // 元 -> 分，四舍五入防浮点误差
    return this.stripe.chargeInCents(cents); // 转手交给第三方
  }
}

// 客户端：只认 PaymentProcessor，根本不知道有 Stripe 这回事
function checkout(processor: PaymentProcessor, amount: number): void {
  console.log(`应付金额：¥${amount.toFixed(2)}`);
  console.log(processor.pay(amount));
}

checkout(new StripeAdapter(new StripePayment()), 128.5);

看懂这段代码，就看懂了整个模式

适配器总共就干三件事：实现目标接口、持有被适配者、把调用翻译过去。它一行业务逻辑都不写，就是个纯转换头——越薄越好。

⚖️ 什么时候用，什么时候别用

✅ 适合的场景

  • 想用一个现成的类，但它的接口跟你的规范对不上，又改不了它的源码（第三方库、老代码）
  • 要接入多个第三方实现，想让业务代码只依赖一套统一接口
  • 两边只是单位、命名、异常风格不一致，需要一层"翻译"

❌ 不适合的场景

  • 接口就一个地方用、差异就一两行——直接包个函数得了，别整个类
  • 系统是你自己新写的——一开始就把接口设计对，别先乱设计再靠适配器打补丁
  • 适配器越写越厚、塞满了 if——那不是翻译问题，是该重构了

⚠️ 容易踩的坑

  • 把适配器当杂物间。翻译就好好翻译，别往里塞业务逻辑——否则第三方一换，业务逻辑跟着陪葬。
  • 一个适配器伺候太多接口。翻译支付又翻译物流还翻译日志，长成上帝类，改一处崩一片。
  • 选错适配方式。"类适配器"靠多重继承，TypeScript/Java 这类单继承语言玩不转；老实用"对象适配器"（组合持有），就像本仓库这样。
  • 胶水逻辑泄漏。单位换算这种事只能活在适配器里，一旦漏到调用方，等于白干。

🔗 和其他模式的关系

  • 和装饰器模式最容易混：都是"包一层"。区别在目的——适配器是改接口形状（对不上→对上），装饰器是加职责（功能变多），接口不变。
  • 和外观模式同属"中间加一层"：适配器只翻译一个类的接口，外观是把一堆类打包成一个简单入口。
  • 和桥接模式是一先一后：桥接是提前设计好两边分离、各自变化；适配器是事后补救已经对不上的接口。
一 句 话 记 住 它 接口对不上，谁也别硬改——中间垫个转换头，两边都舒坦。
