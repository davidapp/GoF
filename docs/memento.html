备忘录模式 Memento

一句话：把对象此刻的模样拍成一张"快照"存到外面，干砸了随时掏出来一键复原。

← 上一个中介者模式 下一个 →观察者模式

🌰 生活里的例子

游戏存档

打 BOSS 之前，你先存个档：游戏把此刻的血量、装备、所在位置统统写进一个存档文件。结果真打输了，读档，一切回到存档那一刻，装备一件没丢。

注意一个细节：存档文件对你来说是个黑盒。你不需要看懂里面存的是什么格式，更不该手改它——手改存档，十有八九把存档改坏。你（玩家）只干两件事：把存档放进存档槽，需要时取出来还给游戏。

对应到模式里：游戏是"发起人"（它会存档也会读档），存档文件就是"备忘录"（黑盒快照），你这位管存档槽的玩家是"管理者"（只保管，从不打开看）。会造快照、会读快照的只有游戏自己。

😖 没有它会怎样

本仓库的例子是一个文本编辑器 TextEditor，要做"撤销（undo）"功能。最直接的写法：把内容公开，让外面的代码自己抄一份存着。

直来直去的写法（问题代码）

编辑器被迫敞开大门：content 做成公开字段，再配上 getContent() / setContent() 随便进出。外面的"历史记录"自己动手抄内容：history.push(editor.getContent())，撤销时再 editor.setContent(history.pop())。

眼下能跑，后患无穷：

  • 编辑器被扒光：内部状态全公开，任何代码都能顺手改一把，封装（把内部数据藏起来只留出入口）算是彻底破了。
  • 加一个字段，全城戒备：编辑器下个月要加"光标位置、字体大小"，外面所有抄状态的代码都得跟着改——因为外面"懂"它的内部结构，缠在一起了。
  • 存法一换就连锁反应：历史记录想换个存法（比如只存增量），编辑器也得跟着动，谁都别想单独改。

根子上的问题：不该让外人懂对象的内部状态。快照该由对象自己打包、自己解读，外人只当搬运工。

👥 角色构成（这个模式由几块拼成）

角色大白话职责本仓库示例里是谁
发起人 Originator 状态的主人：会把自家状态打包成快照，也会从快照读回来。全世界只有它懂快照的格式。 TextEditor（save() / restore()）
备忘录 Memento 快照本身：装着某一刻的完整状态，对外只读，像个黑盒子。 EditorMemento
管理者 Caretaker 仓库保管员：只负责收快照、发快照（压栈 / 出栈），从不打开偷看里面装了什么。 History

解耦（把缠在一起的代码拆开，互不认识也能合作）的关键：History 和编辑器之间只有一个"存 / 取"的约定。真正懂状态格式的只有 TextEditor 一个——它加十个字段，History 一行都不用改。

🗺️ 结构图（谁认识谁、谁调用谁）

🔄 运转步骤（跑一遍完整流程）

  1. 输入：editor.type("第一段内容。")，内容写进编辑器。
  2. 打快照：调用 editor.save()，编辑器把当前的 content 装进一个新建的 EditorMemento。
  3. 入库：history.push(快照)，保管员把它压进栈底，看都没看一眼。
  4. 继续写：又输入"第二段内容。"再存一张快照 2；接着写"第三段内容（写错了，待会撤销）。"——这步故意不存。
  5. 撤销：history.pop() 摸出最近一张快照（快照 2），交回 editor.restore()。
  6. 复原：编辑器从快照里读回内容，文本回到"第一段 + 第二段"。再 pop 一次还能撤到快照 1——多级撤销就是这么摞出来的。

🔍 代码走读

下面是本仓库 TypeScript 实现的骨架（完整版见 ts/memento/main.ts，有删减）：

ts/memento/main.ts（简化）
// 备忘录：一个只读的"快照"，只有编辑器自己会用它
class EditorMemento {
  constructor(private readonly content: string) {}
  getContent(): string {
    return this.content;
  }
}

// 发起人：唯一懂"状态怎么存、怎么取"的人
class TextEditor {
  private content = "";

  type(text: string): void { this.content += text; }

  save(): EditorMemento {                   // ① 把当前状态拍成快照
    return new EditorMemento(this.content);
  }

  restore(memento: EditorMemento): void {   // ③ 撤销时从快照读回来
    this.content = memento.getContent();
  }
}

// 管理者：只管存和取，从不打开快照看内容
class History {
  private readonly mementos: EditorMemento[] = [];

  push(memento: EditorMemento): void { this.mementos.push(memento); }
  pop(): EditorMemento | undefined { return this.mementos.pop(); }  // ② 撤销时取最近一张
}

看懂这段代码，就看懂了整个模式

整个模式的核心就一句："存"和"取"都经过发起人的手，管理者只当快递员。快照对管理者是不可见的黑盒，所以封装一点没破；快照摞在栈里，所以能一路撤到底。

⚖️ 什么时候用，什么时候别用

✅ 适合的场景

  • 需要撤销 / 回滚：编辑器 undo、游戏读档、数据库事务回滚
  • 想保存和恢复对象内部状态，又不想把内部字段公开
  • 要多级撤销——不只撤一步，能一路撤回历史任意一刻

❌ 不适合的场景

  • 状态特别大或快照特别频繁——每张快照都是完整拷贝，内存吃不消
  • 压根不需要回头的操作（一次性计算、流水式处理）——存快照纯属浪费
  • 状态里攥着文件句柄、网络连接这类外部资源——快照存不下也恢复不了

⚠️ 容易踩的坑

  • 快照又大又密 → 内存爆炸。每按一次键就存一张全量快照，历史列表越长占得越多。大对象要改增量快照，或限制历史长度。
  • 管理者偷看偷改快照 → 封装破防。快照只能原样转交，一旦有人绕过发起人直接改快照内容，"恢复"就恢复出脏数据了。
  • 备忘录做成可变的 → 神不知鬼不觉被改。快照应当只读（本仓库的 content 就是 readonly），拍照那一刻就定格，不许再动。
  • 只恢复了内存，忘了恢复外部世界。编辑器内容回去了，界面没刷新、关联文件没同步，用户看到的还是错的。

🔗 和其他模式的关系

  • 和命令模式是撤销功能的黄金搭档：命令记录"你做了什么"（可以反向执行来撤销），备忘录记录"当时长什么样"（直接恢复快照）。
  • 原型模式也能复制对象，但那是完整克隆一个新对象拿去用；备忘录是黑盒快照，专门为了存起来等日后恢复。
  • 想实现"重做 / 时间线"要在历史快照列表里来回走，可以配合迭代器模式遍历这些快照。
