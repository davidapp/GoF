访问者模式 Visitor

一句话：把"对一堆对象做的操作"整个搬到外面的访问者对象里——原来的类一行不改，就能天天加新操作。

🌰 生活里的例子

医院病房查房

病房里住着一排病人：有的是骨科的，有的是眼科的。今天抽血队来查房，见到骨科病人按骨科的流程抽，见到眼科病人按眼科的流程抽；明天换成拍片队，还是这批病人，流程又换成拍片的。

注意一个细节：病人从头到尾没换过病房、没改过病历，他们只做一件事——配合检查，并亮明身份"我是骨科的"。至于"见到骨科病人该干什么"，那是查房队自己的事：抽血队有一套，拍片队有另一套。

对应到模式里：病人是"元素"（各自亮身份），病房是"对象结构"，查房队是"访问者"——每支队伍身上带着"见到每种病人该怎么办"的一整套规程。换一支队伍，就是换一种操作，病人自己毫发无损。

😖 没有它会怎样

本仓库的例子是一组图形：Circle（圆）和 Rectangle（矩形）混在一个数组里，想对它们"求面积"。最直接的写法：遍历时挨个问"你是谁"。

直来直去的写法（问题代码）

用 instanceof 链一个个认：

if (s instanceof Circle) total += Math.PI * s.radius ** 2;
else if (s instanceof Rectangle) total += s.width * s.height; ……

过两天要加"渲染绘制"？再抄一遍这条 instanceof 链，里面换成画图的代码。

每加一种操作就抄一遍判断链，越抄越糟：

  • 判断链到处复制：求面积一份、渲染一份、导出又一份，全散在客户端代码里，改个判断要改 N 处。
  • 想把操作写进图形类里？改不动：Circle、Rectangle 若是别人维护的库代码，你根本无权往里加方法。
  • 新增一种图形就全城搜捕：加了"三角形"，所有操作里的 instanceof 链都得补一支，漏一处就悄悄算错。

根子上的问题：操作和元素类型缠在了一起，还双向都不好改。访问者把"操作"整套搬出去集中管理，两头都松绑。

👥 角色构成（这个模式由几块拼成）

角色大白话职责本仓库示例里是谁
元素接口 Element 只要求会一件事：accept(visitor)——接待访问者，并把自己的真实身份交出去。 Shape 接口
具体元素 被检查的人：在 accept 里点名叫访问者执行"针对我这种类型"的方法。 Circle、Rectangle
访问者接口 Visitor 查房规程：为每种具体元素各准备一个专属方法（见到圆怎么办、见到矩形怎么办）。 ShapeVisitor 接口（visitCircle / visitRectangle）
具体访问者 一支支查房队：每支队伍把"一种操作 × 每种元素"的答案全部自带在身上。 AreaVisitor、DrawVisitor
对象结构 那间病房：一堆元素摆在一起，供访问者挨个走一遍。 演示里的 shapes: Shape[] 数组

解耦（把缠在一起的代码拆开，互不认识也能合作）的关键：靠"双分派"精确路由——第一次分派在 accept() 里确定"元素是哪种"，第二次在 visitXxx() 上确定"操作是哪种"，两者一组合就命中"类型 × 操作"的正确答案，全程不用一个 instanceof。

两次分派：accept() 先确定"元素是哪种"，visitXxx() 再确定"操作是哪种"——换一支访问者队伍，就是换一种操作，图形类一行不改。

🔄 运转步骤（跑一遍完整流程）

  1. 摆摊：准备 shapes 数组：Circle(5)、Rectangle(4, 6)、Circle(2)、Rectangle(10, 3) 混着放。
  2. 请人：new DrawVisitor() 进场，先做渲染这支队伍。
  3. 逐个接待：for 循环里每个 shape.accept(drawVisitor)——元素只负责接待。
  4. 亮身份：Circle 的 accept 里调 visitor.visitCircle(this)，自己把类型报出来。
  5. 干活：DrawVisitor 的 visitCircle 知道眼前是圆，打印"绘制 ○ 圆形，半径=5"；矩形同理。
  6. 换人重来：换成 AreaVisitor 再遍历一遍，同样的 accept 流程，这次每个图形算出面积并累加出总面积——图形类一行没改。

🔍 代码走读

下面是本仓库 TypeScript 实现的骨架（完整版见 ts/visitor/main.ts，有删减）：

ts/visitor/main.ts（简化）
// 访问者接口：为每种元素准备一个专属方法
interface ShapeVisitor {
  visitCircle(circle: Circle): void;
  visitRectangle(rectangle: Rectangle): void;
}

// 元素接口 + 具体元素：唯一的本事是"亮明身份"
interface Shape {
  accept(visitor: ShapeVisitor): void;
}

class Circle implements Shape {
  constructor(public readonly radius: number) {}

  accept(visitor: ShapeVisitor): void {
    visitor.visitCircle(this);   // 双分派：把具体类型交给访问者
  }
}

// 具体访问者：求面积（想加新操作就再写一个访问者，图形类不动）
class AreaVisitor implements ShapeVisitor {
  private totalArea = 0;

  visitCircle(circle: Circle): void {           // 圆有圆的算法
    this.totalArea += Math.PI * circle.radius ** 2;
  }

  visitRectangle(rectangle: Rectangle): void {  // 矩形有矩形的算法
    this.totalArea += rectangle.width * rectangle.height;
  }
}

// 使用：同一组图形，换一个访问者就是换一种操作
for (const shape of shapes) {
  shape.accept(areaVisitor);    // 全程没有一个 instanceof
}

看懂这段代码，就看懂了整个模式

核心就一对手拉手的调用：shape.accept(visitor) 进去，visitor.visitCircle(this) 出来。元素报类型、访问者接类型，两步接力之后，"求面积的圆"和"渲染的圆"各自找到各自的那段代码，谁也不用改谁。

⚖️ 什么时候用，什么时候别用

✅ 适合的场景

  • 元素种类稳定（圆、矩形就这几种），操作经常加（求面积、渲染、导出、校验……）
  • 不能或不想改元素类的代码——第三方库、别人维护的历史代码
  • 同一个结构上要施加好几种互不相关的操作，想把每种操作各自收拢成一个类

❌ 不适合的场景

  • 元素种类还在频繁增加——每加一种元素，访问者接口和所有已有实现都得改，正好把长处反过来戳
  • 元素就一两种、操作也就一个——直接写方法调用，三行搞定的事别请查房队
  • 元素想把内部数据藏严实——访问者必须读到足够的数据（半径、宽高）才能干活，封装注定要开个大口子

⚠️ 容易踩的坑

  • 元素类型一多，访问者先撑不住。十种图形 × 每个访问者十个方法，新增一种图形要改全体访问者——这就是本仓库 README 强调的前提："稳定元素、频繁扩展操作"，反过来就别用。
  • 双分派没走对，回头用 instanceof 糊弄。一旦在遍历里写起类型判断，模式就名存实亡，等于绕一圈回到老路。
  • 访问者顺手动了元素的状态。一支队伍跑完把图形数据改了，下一支队伍看到的就是脏数据——访问者应当只读不写（本仓库 radius、width 都是只读的）。
  • 新增元素时漏改某个旧访问者。运气好编译期报"接口没实现全"，运气差运行到那行才炸——改动时记得全量搜索所有访问者。

🔗 和其他模式的关系

  • 和迭代器模式是黄金搭档：迭代器负责"挨个走一遍"对象结构，访问者负责"走到每个元素身上干什么"，两边各司其职。
  • 和组合模式的经典组合：树形结构（文件夹、UI 控件树）配上访问者，对整棵树上的各种节点统一施加操作。
  • 和装饰器模式都在给对象加行为：装饰器把行为"包"在对象外面、接口不变；访问者把操作整套搬到另一个对象里，靠双分派路由。
一 句 话 记 住 它 队伍原地不动，专家轮着上门：来了谁，就干谁的活。
