解释器模式 Interpreter

一句话：给一种简单的小语言定一套规则类，把句子拆成一棵树，顺着树把意思"解释"出来。

← 上一个命令模式 下一个 →迭代器模式

🌰 生活里的例子

"爸爸的哥哥的儿子"是谁？

过年饭桌上长辈考你："你爸爸的哥哥的儿子，你该叫什么？"你脑子里其实是这么算的：先定位"爸爸"这个人 → 在家谱里找"他的哥哥" → 再找"哥哥的儿子" → 得出"堂哥"。

注意两个细节：这套"的某某"的推算规则是固定的，谁家都通用；换一本家谱（比如从妈妈那边算），同样的规则照样能算，只是查的册子换了。

这个比喻对应模式里的什么："的哥哥""的儿子"这些推算规则 = 一个个非终结符表达式类（枝干节点，负责把两边的算合起来）；"爸爸"这种具体的人 = 终结符表达式（叶子节点，直接给答案）；整串称呼 = 句子；家谱名册 = Context 上下文（存着"每个名字对应谁"的对照数据）；一层层往里推 = interpret() 递归求值。

😖 没有它会怎样

本仓库的场景是算术表达式：程序要算 "5 + 3 - 2"、"x + 20 - y" 这种式子。最直接的写法是每来一个式子就手写一个函数：

直来直去的写法（问题代码）

一个式子配一个函数，硬编码：

function calc1() { return 5 + 3 - 2; } —— 专门算这一句

function calc2(x, y) { return x + 20 - y; } —— 换个式子再写一个

这样写眼下能跑，但麻烦在后头：

  • 表达式是运行时才知道的（用户输进来的、配置文件里读来的），你根本没法提前把函数写好。
  • 式子变一点就得新写一个函数；哪天要支持乘除，老函数全部重写。
  • "按规则解读一句话"的逻辑散落在各处，没有统一的地方管规则、查变量。

根子上的问题是把"一句一句的式子"当成了代码，而它们其实是数据——是数据就该被解析、被解释，而不是被手写。

👥 角色构成（这个模式由几块拼成）

角色大白话职责本仓库示例里是谁
抽象表达式 定规矩："每个语法节点都得会自己算出自己的值"。 Expression 接口
终结符表达式（叶子） 推到头了的节点：数字直接报数，变量翻家谱（查上下文）。 NumberExpression、VariableExpression
非终结符表达式（枝干） 复合节点：手里攥着左右两棵子树，先递归算两边，再把结果合起来（相加/相减）。 AddExpression、SubtractExpression
上下文 Context 一本"家谱名册"：变量名 → 数值的对照表，可以随时改。 Context 类
解析器 + 客户端 把 "x + 20 - y" 这样的字符串一句句拆开、搭成树，再发动求值。 parseExpression()、main()

解耦关键在哪：每种语法规则一个类，规则长在类里而不是长在 if/else 里。想支持乘法？新增一个 MultiplyExpression 类，老的表达式类一个都不用动——这就是解耦（把缠在一起的代码拆开，互不认识也能合作）。而且树搭好以后可以反复用：换本"家谱"（改 Context 里的变量）就能重算，不用重新解析。

这就是一棵语法树：叶子（数字/变量）自己报数，枝干（加减）把左右两边递归算出的结果合并。对 "x + 20 - y" 来说，把叶子换成变量，值从 Context 查。

🔄 运转步骤（跑一遍完整流程）

  1. 备好上下文：造一个 Context，登记 x=10、y=4——相当于备好家谱名册。
  2. 分词：parseExpression("x + 20 - y") 按空格把句子切成一个一个词。
  3. 搭树：先拿下第一个词当左叶子，往后每碰到一个 +/-，就把"已有结果"和"下一个词"包成一个新的加/减节点——从左到右，越包越厚。
  4. 求值：对树根调 interpret(context)——枝干先递归问左右子树，叶子直接报数（变量就查 Context），一层层把 26 算出来。
  5. 复用重算：把 Context 改成 x=100，对同一棵树再 interpret() 一次，直接得 116——树不用重建。

🔍 代码走读

下面是本仓库 TypeScript 实现的骨架（完整版见 ts/interpreter/main.ts，有删减）：

ts/interpreter/main.ts（简化）
// 上下文：变量名 → 数值 的对照表（家谱名册）
class Context {
  private readonly variables = new Map<string, number>();
  setValue(name: string, value: number): void { this.variables.set(name, value); }
  getValue(name: string): number {
    const value = this.variables.get(name);
    if (value === undefined) throw new Error(`未定义的变量: ${name}`);
    return value;
  }
}

// 抽象表达式：每个语法节点都会"自我求值"
interface Expression {
  interpret(context: Context): number;
}

// 终结符（叶子）：数字直接返回；变量去查上下文
class NumberExpression implements Expression {
  constructor(private readonly value: number) {}
  interpret(_context: Context): number { return this.value; }
}

// 非终结符（枝干）：先递归算左右子树，再把结果合并
class AddExpression implements Expression {
  constructor(
    private readonly left: Expression,
    private readonly right: Expression,
  ) {}
  interpret(context: Context): number {
    return this.left.interpret(context) + this.right.interpret(context);
  }
}

// 解析器把 "x + 20 - y" 搭成上面这类节点组成的树
const expr = parseExpression("x + 20 - y");
expr.interpret(context);  // → 26；改 x=100 再 interpret 一次 → 116

看懂这段代码，就看懂了整个模式

核心就一行：AddExpression 里的 left.interpret(context) + right.interpret(context)——枝干把问题拆给左右子树，叶子给出答案，递归到底，整棵树的值就出来了。加减如此，乘除、与或，都是一个道理。

⚖️ 什么时候用，什么时候别用

✅ 适合的场景

  • 语法简单、规则固定的小语言：算式、权限表达式（"admin AND NOT banned"）、筛选条件
  • 每条文法规则能对应一个类，规则数量不多，类不会失控
  • 同一棵树要换着数据反复求值：改改 Context 里的变量就能重算，树不用重建

❌ 不适合的场景

  • 语法复杂或性能敏感——用现成的解析器、规则引擎，别手搓
  • 文法规则特别多——每种规则一个类，几十个类堆在那，改一条文法牵连一片
  • 只是算个写死的公式——直接写函数，三行搞定的事别上二十个类

⚠️ 容易踩的坑

  • 类爆炸。"加"一个类、"减"一个类、"乘"再一个类……类的数量跟着文法规则走，读代码要在十几个文件之间跳。
  • 递归太深会爆栈。表达式嵌套一百层，interpret 就要递归一百层。解析用户输入时尤其要设防（比如限制表达式长度）。
  • 变量没定义，运行时才炸。Context 里忘了 setValue，一路求值到叶子才抛"未定义的变量"。最好解析完先统一检查一遍。
  • 优先级没处理对。本例只有加减、同优先级左结合，所以简单；一旦混入乘除，解析器必须先处理优先级，否则 2 + 3 * 4 会被算成 10。

🔗 和其他模式的关系

  • 语法树本身就是组合模式的应用：叶子是数字/变量，枝干是运算节点，整棵树统一用 Expression 接口递归。
  • 想给同一棵树加新操作（打印、检查变量、求值……）而不改动节点类，配上访问者模式。
  • 重复出现的叶子（比如同一个数字到处用）可以做成共享对象，用享元模式省内存。
一 句 话 记 住 它 把句子拆成一棵树，每个节点自己会算；树搭一次，换本"词典"（上下文）就能反复算。
