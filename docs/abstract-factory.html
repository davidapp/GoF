抽象工厂模式 Abstract Factory

一句话：一个工厂不造单件，专造"成套"的——换风格时整套连着换，绝不出现混搭。

← 总览返回首页 下一个 →建造者模式

🌰 生活里的例子

去家具城买"整套家具"

你跑进家具城，跟导购说："我家要北欧风，客厅三件套来一套。"导购直接给你配齐北欧风沙发、北欧风茶几、北欧风电视柜——绝对不会给你塞一个雕花红木沙发进来。哪天改主意要中式风？还是一句话的事：整套退回，换一整套中式的进来。

你自始至终没关心过"沙发是哪个木匠做的"，你只说了两件事：要哪几样（沙发、茶几、电视柜），要哪种风（北欧还是中式）。

翻译成模式的语言："风格"就是产品族（Windows 风 / macOS 风），"沙发、茶几"这些品类就是抽象产品（按钮、复选框），导购背后的家具厂就是具体工厂。你要的从来不是某个单件，而是"一整套配套的"。

😖 没有它会怎样

本仓库的示例是跨平台界面库：同一套界面代码，在 Windows 上要长 Windows 的样子，在 macOS 上要长 macOS 的样子。最直接的写法，是在每个用控件的地方现场判断平台：

直来直去的写法（问题代码）

界面上每画一个控件，都来这么一段：

if (platform === "windows") btn = new WindowsButton()
else if (platform === "macos") btn = new MacButton() ……

复选框再来一遍，滑块再来一遍，一百个页面各来一遍。

这样写的下场：

  • if/else 满天飞：一百处用控件的地方就有一百段平台判断，明天加个 Linux 平台，改一百处，漏一处就是 bug。
  • 可能混搭出错：哪处手滑写了 new MacCheckbox() 配 new WindowsButton()，界面立刻"精神分裂"，编译器还不报错。
  • 界面代码被迫认识所有具体类：Windows、Mac 的类名缠满业务代码，解耦（就是把缠在一起的代码拆开，互不认识也能合作）无从谈起。

根子上的问题是"选货"这件事散落在各处，而它本该集中到"厂子"里，一次定好一整套。

👥 角色构成（这个模式由几块拼成）

角色大白话职责本仓库示例里是谁
抽象产品 给"这类东西能干什么"定规矩，只定能力、不问出身。 Button、Checkbox 接口
具体产品 各家风的具体货：方形边框的 Windows 按钮、圆形的 macOS 复选框…… WindowsButton、WindowsCheckbox、MacButton、MacCheckbox
抽象工厂 一张供货清单，只宣布"我能造按钮和复选框"，别的不问。 GUIFactory 接口
具体工厂 真正的厂子，每家只造本平台的成套货。 WindowsFactory、MacFactory
客户端 使用方，从头到尾只跟抽象接口说话。 renderUI() 函数

解耦关键：renderUI() 里从头到尾没出现 Windows、Mac 任何一个字——它只认识 GUIFactory、Button、Checkbox 三张"合同"。往里塞哪家工厂，就出哪家货，客户端一行都不用改。

🔄 运转步骤（跑一遍完整流程）

  1. 选厂：程序启动时 createFactory("windows") 按平台拿到 WindowsFactory。
  2. 开工：renderUI(factory) 被调用，它只管伸手要货：factory.createButton()。
  3. 造货：工厂内部 new WindowsButton()，但返回类型是抽象的 Button——具体身份被抹掉，只留能力。
  4. 配套拿齐：再要 createCheckbox()，拿到的必然是 WindowsCheckbox，同一家厂出的，绝不混搭。
  5. 使用：界面代码调 button.render()、checkbox.toggle()，画出来就是 Windows 风格。
  6. 换族：把 "windows" 改成 "macos"，renderUI 一字不改，整套控件变成 mac 风。

🔍 代码走读

下面是本仓库 TypeScript 实现的骨架（完整版见 ts/abstract-factory/main.ts，有删减）：

ts/abstract-factory/main.ts（简化）
// 抽象产品：只约定"控件能干什么"，不问是哪家的
interface Button {
  render(): string;
  onClick(): string;
}
interface Checkbox {
  render(): string;
  toggle(): string;
}

// 抽象工厂：一张供货清单，声明"我造哪几样"
interface GUIFactory {
  createButton(): Button;
  createCheckbox(): Checkbox;
}

// 具体工厂：只造 Windows 风格的成套控件
class WindowsFactory implements GUIFactory {
  createButton(): Button { return new WindowsButton(); }
  createCheckbox(): Checkbox { return new WindowsCheckbox(); }
}

// 客户端：全程只跟抽象接口说话，没出现任何平台字样
function renderUI(factory: GUIFactory): void {
  const button = factory.createButton();     // 闭眼拿货
  const checkbox = factory.createCheckbox(); // 必然同族
  console.log(button.render());
  console.log(checkbox.render());
}

看懂这段代码，就看懂了整个模式

眼睛盯住 renderUI：它拿到的是 GUIFactory 这张合同，根本不知道背后是哪家厂。main() 里 createFactory("macos") 一换，同一行代码出的是另一套货——换工厂 = 换整套风格，这就是全部魔法。

⚖️ 什么时候用，什么时候别用

✅ 适合的场景

  • 产品天然成族出现、必须配套，混搭就是事故（UI 控件、数据库方言）
  • 系统要在多套产品族之间整体切换，而且最好一处切换
  • 想对客户端隐藏具体产品类，只暴露抽象接口

❌ 不适合的场景

  • 产品种类经常增加——每加一样，工厂接口和所有具体工厂都得改
  • 只需要造一样东西，没有"配套"一说——工厂方法就够了
  • 几类产品之间毫无关联，硬凑成一个"族"纯属自找麻烦

⚠️ 容易踩的坑

  • 加新产品 = 接口大地震。GUIFactory 想加一个 createSlider()，接口一改，所有具体工厂全部要跟着改。产品结构不稳的项目慎用。
  • 类数量爆炸。N 个平台 × M 种控件 = N×M 个具体产品类，小项目用它等于自找罪受。
  • 换族只在"发牌时"方便。工厂在创建时传进去，对象已经 new 出来了，程序跑到一半想整套换风格？难。
  • 和工厂方法傻傻分不清。记口诀：工厂方法造"一个"，抽象工厂造"一族"。

🔗 和其他模式的关系

  • 和工厂方法模式最容易混：工厂方法靠子类重写、只负责造"一个"产品；抽象工厂靠组合（把工厂对象传进来）、负责造"一整族"。
  • 常和建造者模式配合：抽象工厂决定"用哪家厂的套件"，建造者负责"复杂的大家伙怎么一步一步攒起来"。
  • 具体工厂常被做成单例模式——一个厂子造一次就够了，全局共用一个 WindowsFactory。
一 句 话 记 住 它 选的不是一件货，是一整套；想换风格？换个厂就行。
