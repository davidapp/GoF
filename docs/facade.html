外观模式 Facade

一句话：给一堆复杂操作装个总开关：你只按一下，它替你把里里外外按顺序全办妥。

🌰 生活里的例子

餐厅的服务员

下馆子你只跟服务员说一句"来份 158 的双人套餐"，后厨立马忙起来：凉菜间切碟、热菜间颠勺、主食间蒸饭、按先凉后热的顺序上桌——这整套流程你一样都不用管，也不用进后厨指挥任何一个师傅。

注意：服务员并没有替后厨做菜，师傅们的手艺一样没少；她只是把"点一套菜"翻译成"后厨的一串协作"，并记住了出菜顺序这个门道。

对应到模式里：顾客是客户端，服务员是外观，后厨各岗位是子系统，"点套餐"就是外观对外的那个简单方法。复杂度没消失，只是被收进了服务员的脑子里。

😖 没有它会怎样

本仓库的例子是家庭影院：想看个电影，背后是投影仪、功放、灯光、播放器四个设备，各有各的遥控器。没有外观时，每次看电影都得手动来一遍：

直来直去的写法（问题代码）

客户端亲自指挥四个设备，顺序还得背对：

lights.dim(20) → projector.turnOn() → projector.setInput("HDMI-Streaming") → amplifier.turnOn() → amplifier.setVolume(15) → player.play(movie) ……

这样写眼下能跑，但麻烦在后头：

  • 六步顺序一步不能错（投影没开就切输入源，白切），来个朋友想看电影，你得先教他半小时。
  • 想再写个"结束观影"，又得反着背一遍：停播、关功放、关投影、灯亮——抄一遍就多一处会写错的地方。
  • 客户端被迫成为四个设备的操作专家，设备一升级（接口改名），所有看电影的代码全得跟着改。

根子上的问题是："先做什么后做什么"这种门道，散落在每个调用方手里，而不是被收在一个地方。

👥 角色构成（这个模式由几块拼成）

角色大白话职责本仓库示例里是谁
外观 Facade 总开关：对外就几个大白话按钮，对内按正确顺序指挥所有子系统。记住的是"流程"，不是"手艺"。 HomeTheaterFacade（watchMovie / endMovie）
子系统们 各管一摊的师傅：灯光调亮暗、投影仪开关切源、功放管声音、播放器管放片，照常暴露自己全部接口。 Lights、Projector、Amplifier、StreamingPlayer
客户端 只想看电影的普通人：一行 watchMovie("星际穿越") 搞定，后厨的事一概不知。 main()

解耦（把缠在一起的代码拆开，互不认识也能合作）关键在：外观封装的其实不是功能，而是"调用顺序"这个隐性知识——先调暗灯、再开投影、最后放片。客户端和子系统互相不认识，都只认识外观；而且外观没有锁门，发烧友仍然可以直接拿 Projector 自己调，外观只是提供了条更好走的路。

箭头方向 = 调用方向：只有外观调子系统，子系统从不认识外观，更不互相聊天——这是它和中介者模式最大的区别。

🔄 运转步骤（跑一遍完整流程）

  1. 各就各位：四个子系统对象（投影仪、功放、灯光、播放器）先建好，照常暴露各自的接口。
  2. 装总开关：HomeTheaterFacade 构造时把这四个家伙统统收进来。
  3. 按按钮：客户端调 homeTheater.watchMovie("星际穿越")——就这一行。
  4. 内部指挥：调暗灯光到 20% → 开投影仪 → 切到 HDMI → 开功放 → 音量设 15 → 播放器放片，六步一气呵成。
  5. 一键收尾：看完调 endMovie()，反着来一遍——停播、关功放、关投影、灯光恢复。
  6. 想微调也行：觉得音量小？发烧友直接绕过外观调 amplifier.setVolume(20)——外观不拦人，它只是条捷径。

🔍 代码走读

下面是本仓库 TypeScript 实现的骨架（完整版见 ts/facade/main.ts，有删减）：

ts/facade/main.ts（简化）
// 子系统们：各管一摊，照常暴露自己的全部接口
class Projector {
  turnOn(): void { console.log("投影仪：开启"); }
  setInput(source: string): void { console.log(`投影仪：切换输入源为 ${source}`); }
  turnOff(): void { console.log("投影仪：关闭"); }
}

class Lights {
  dim(level: number): void { console.log(`灯光：调暗至 ${level}%`); }
  brighten(): void { console.log("灯光：恢复明亮"); }
}
// 功放 Amplifier、播放器 StreamingPlayer 同理，略

// 外观：对外两个按钮，对内按正确顺序指挥
class HomeTheaterFacade {
  constructor(
    private readonly projector: Projector,
    private readonly amplifier: Amplifier,
    private readonly lights: Lights,
    private readonly player: StreamingPlayer,
  ) {}

  watchMovie(movie: string): void {
    this.lights.dim(20);                        // 1 先调暗灯光
    this.projector.turnOn();                    // 2 开投影仪
    this.projector.setInput("HDMI-Streaming");  // 3 切输入源
    this.amplifier.turnOn();                    // 4 开功放
    this.amplifier.setVolume(15);               // 5 设音量
    this.player.play(movie);                    // 6 最后才放片
  }

  endMovie(): void { /* 反着收尾，略 */ }
}

// 客户端：一行搞定，四个设备一个都不认识
const homeTheater = new HomeTheaterFacade(
  new Projector(), new Amplifier(), new Lights(), new StreamingPlayer(),
);
homeTheater.watchMovie("星际穿越");

看懂这段代码，就看懂了整个模式

外观类里没有一行自己的业务，全是"按什么顺序调谁"。它真正的价值是把那串顺序知识从每个客户端的脑子里搬进了这一个类——顺序改了，只改这一处。

⚖️ 什么时候用，什么时候别用

✅ 适合的场景

  • 子系统挺复杂，但大多数人只用其中固定的几套流程——包个总开关最省心
  • 想给一堆老代码包个干净的新入口，新代码只认门面不碰内脏
  • 分层架构里给每层安个门面，层与层之间只走门面

❌ 不适合的场景

  • 子系统就两三个类、每类一两个方法——直接调用反而最清楚
  • 客户端几乎每次都要深度定制流程、绕过门面——门面形同虚设
  • 把几十种操作全堆进一个门面方法——那是造上帝类，不是造门面

⚠️ 容易踩的坑

  • 外观变上帝类。观影、听歌、打游戏、开窗帘全往一个类里塞，最后谁也不敢动它——需求多了就拆成多个外观，一个场景一个。
  • 以为外观"锁死"了子系统。它只是推荐路线，子系统的公开接口照常能用；文档和团队约定要跟上，别自欺欺人。
  • 外观和子系统双向纠缠。子系统反过来调外观、或外观里塞进子系统的状态判断，单向的简单关系就被搅成蜘蛛网。
  • 把外观当中介者用。子系统之间需要互相协调、你来我往时，外观（单向传话）不够用，那活该中介者上场。

🔗 和其他模式的关系

  • 和中介者模式最容易混：外观是单向传话筒（客户端 → 外观 → 子系统，子系统之间互不认识）；中介者是双向的，专门协调一群互相认识的对象。
  • 外观常做成单例——一个家一台总开关，没必要人手一个。
  • 和适配器模式同属"包一层"：适配器翻译一个类的接口形状，外观简化一群类的调用流程。
一 句 话 记 住 它 复杂流程装个总开关：你只按一下，顺序和门道它全包了。
