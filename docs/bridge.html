结构型

桥接模式 Bridge

一句话：两个各自会变的东西，别用继承焊死——中间搭座桥，各变各的，随便组合。

← 上一个适配器模式 下一个 →组合模式

🌰 生活里的例子

万能遥控器和电器

遥控器和电器是分开卖的：遥控器有普通款、高级款；电器有电视、收音机、音响……但没有哪家会生产"电视专用高级遥控器""收音机专用普通遥控器"这种专用货。

凭什么能分开？因为双方都守同一套红外指令标准：遥控器只管发"开机、调音量"这些指令，至于是电视还是收音机在听，它不关心；电器只管认指令干活，也不知道遥控器是高级还是普通。

对应到模式里：遥控器是"抽象"那一侧，电器是"实现"那一侧，那套指令标准就是接口，遥控器里揣着的电器引用就是"桥"。两侧各自出新品，随便搭配。

😖 没有它会怎样

本仓库的例子正是遥控器控制设备。如果不用桥接，靠继承硬拼这两种遥控器 × 两种设备的组合：

直来直去的写法（问题代码）

为每种组合各写一个类：

RemoteControlTV、RemoteControlRadio、AdvancedRemoteControlTV、AdvancedRemoteControlRadio ……

2 × 2 = 4 个类，眼下还能忍，但麻烦在后头：

  • 每加一种设备（音响），所有遥控器都得为它生一个娃，类数量翻倍。
  • 每加一种遥控器（语音款），又得把每种设备再抄一遍，再翻倍。
  • 同样的"开关机"逻辑在 4 个类里抄了 4 遍，改个音量步长要改 4 处。

这就是教科书说的类爆炸：两个维度用继承相乘，类的数量是乘积，越加越多。

👥 角色构成（这个模式由几块拼成）

角色大白话职责本仓库示例里是谁
实现接口 Implementor 电器这侧的规矩：想被遥控，就得会开关机、调音量。 Device 接口
具体实现 照规矩干活的电器，各干各的，互相不认识。 TV、Radio
抽象 Abstraction 遥控器这侧：揣着一个 Device 引用——这个引用就是"桥"。干活只调接口，不挑设备。 RemoteControl
扩展抽象 遥控器出新款：加个静音键，照样什么设备都能控。 AdvancedRemoteControl（新增 mute()）

解耦关键在：遥控器不继承任何设备，设备也不继承任何遥控器，两边只靠一个 Device 接口相连。新增音响？只写一个 SoundBar 实现 Device，所有遥控器立刻能用；新增语音遥控器？只写一个遥控器子类，所有电器立刻能被控。两边各自长个儿，互不打扰。

🔄 运转步骤（跑一遍完整流程）

  1. 定标准：先定 Device 接口，规定电器必须会 turnOn、setVolume 这些动作。
  2. 造电器：TV、Radio 各自实现 Device，各管各的开机动画和音量范围。
  3. 搭桥：RemoteControl 构造时收一个 Device 存下来——桥搭好了。
  4. 过桥干活：按电源键，togglePower() 只问 this.device.isOn()，是关的就 turnOn()，根本不关心对面是谁。
  5. 出新款：AdvancedRemoteControl 加一个 mute()，代码里只调 device.setVolume(0)，一行没碰任何电器。
  6. 自由组合：new AdvancedRemoteControl(new Radio())——高级遥控器配收音机，不用专门造一个类。

🔍 代码走读

下面是本仓库 TypeScript 实现的骨架（完整版见 ts/bridge/main.ts，有删减）：

ts/bridge/main.ts（简化）
// 实现接口：设备这一维度，遥控器只认它
interface Device {
  isOn(): boolean;
  turnOn(): void;
  turnOff(): void;
  setVolume(percent: number): void;
  getVolume(): number;
}

// 抽象：遥控器这一维度，怀里揣着 device —— 桥就在这
class RemoteControl {
  constructor(protected device: Device) {}

  togglePower(): void {
    this.device.isOn() ? this.device.turnOff() : this.device.turnOn();
  }

  volumeUp(): void {
    this.device.setVolume(this.device.getVolume() + 10); // 只调接口
  }
}

// 扩展抽象：加静音键，一个字的设备代码都没碰
class AdvancedRemoteControl extends RemoteControl {
  mute(): void {
    this.device.setVolume(0); // 还是只会调 Device 接口
    console.log(`${this.device.getName()} 已静音`);
  }
}

// 两个维度自由组合，不需要"高级电视遥控器"这种专用类
const remote = new AdvancedRemoteControl(new TV());
remote.togglePower();
remote.mute();

看懂这段代码，就看懂了整个模式

整座桥其实就是构造函数里那一个 device 字段：用组合（揣一个引用）代替继承（生一堆子类），两个维度从"相乘"变回"相加"，类数量就不爆炸了。

⚖️ 什么时候用，什么时候别用

✅ 适合的场景

  • 一个东西有两个各自独立变化的维度（遥控器款式 × 设备种类、形状 × 颜色、平台 × 业务）
  • 不想在两个维度之间写死绑定，希望运行时能换其中一端
  • 继承已经开始套娃、类数量按乘积涨——该拆桥了

❌ 不适合的场景

  • 只有一个维度会变——老实用继承，别硬拆两个维度
  • 两个维度其实互相纠缠、拆开后反而要说一堆废话传参
  • 就三五个类的小功能——上桥接纯属过度设计

⚠️ 容易踩的坑

  • 实现接口设计得太大。Device 里塞二三十个方法，每种新电器都要实现一遍用不上的功能，写得想骂人——接口只放两侧都需要的公共动作。
  • 和策略模式混着用。俩结构几乎一样，但桥接是"两个维度长期共存、各自扩展"，策略是"同一个动作的几种做法、随时互换"。定位搞混，架构就长歪了。
  • 偷偷在抽象里 instanceof 设备。一旦遥控器里出现"如果是电视就……"，桥就白搭了，又焊回去了。
  • 桥搭了却不用。抽象侧直接把活全干了不转发给 device，实现侧成了摆设，回到老路。

🔗 和其他模式的关系

  • 和策略模式是双胞胎结构：都是"组合持接口"。区别在意图——桥接是两个维度长期共存各自扩展，策略是同一件事的多种做法运行时互换。
  • 和适配器模式一先一后：桥接是设计期就把两侧分开，适配器是事后补救已经对不上的接口。
  • 实现那一侧的对象常用抽象工厂来造，把"new 哪个设备"也藏起来。
一 句 话 记 住 它 两个各自会变的东西别焊死：中间搭座桥，各长各的，随便搭配。
