单例模式 Singleton

一句话：全程序只此一份，谁来找、什么时候找，拿到的都是同一个它。

← 上一个原型模式 下一个 →适配器模式

🌰 生活里的例子

全公司只有一枚的公章

公司规定：签合同必须盖公章，而公章全公司只此一枚，由行政部保管。谁要盖章，都得走行政部这个窗口——不许自己私刻一枚。行政部第一次收到申请，才把章从保险柜取出来，之后就一直放在手边，谁来都盖这一个。

还有一本用章登记簿：谁在什么时候盖了什么，全公司记的是同一本账。你在登记簿上补一笔，隔壁部门翻开就能看到。

对应到模式里：禁止私刻是 private constructor()，行政部窗口是 getInstance()，那枚章是唯一实例，第一次才取出保险柜是懒加载，同一本登记簿就是所有模块共享的状态。

😖 没有它会怎样

本仓库的示例是全局日志器 Logger：程序里几十个模块都要记日志，还得统一控制日志级别。最直接的写法是每个模块自己 new 一个：

直来直去的写法（问题代码）

模块 A：const loggerA = new Logger()

模块 B：const loggerB = new Logger()

模块 C：const loggerC = new Logger() ……各记各的账。

这样写的麻烦：

  • 行为不一致：模块 A 调 setLevel(DEBUG)，模块 B 手里那个还是 INFO——同一个程序，日志口径却不统一。
  • 日志四散：想查"刚才到底发生了什么"，没有一本完整的账，得挨个对象去翻。
  • 找不到总开关：想统一关掉日志、提高阈值，不知道该去哪儿下手。
  • 白占内存：N 个一模一样的对象，干着一个人的活。

根子上的问题是该共享的被复制成了多份——有些东西天生就该只有一个。

👥 角色构成（这个模式由几块拼成）

角色大白话职责本仓库示例里是谁
单例类 Singleton 那个"只此一份"的类，自己看管自己的唯一实例。 Logger
私有构造函数 门口的禁令：外人休想 new。 private constructor()
静态实例字段 类自己保管的唯一一份，造过就存着。 private static instance
全局访问点 领东西的唯一窗口：第一次来才造，之后直接返。 static getInstance()
共享状态 全程序共用的账本和开关，一处改动全局生效。 logs 数组、level 阈值、setLevel()

解耦关键：所有模块从同一个窗口领到同一个对象，状态天然全局一致——A 改了阈值，B 立刻感知，因为它们手里拿的本来就是同一个 Logger。

🗺️ 结构图（谁认识谁、谁调用谁）

箭头方向 = 调用方向：所有模块最终都落到同一个对象上；new Logger() 这种写法在编译阶段就被私有构造函数拦下。

🔄 运转步骤（跑一遍完整流程）

  1. 堵死歪门：有人手滑写 new Logger()？编译器直接报错——构造函数是 private 的。
  2. 首次申请：模块 A 调 Logger.getInstance()，静态字段里还没实例，于是 new 一个存进去。
  3. 再申请：模块 B 也调 getInstance()，这次静态字段里已经有了，原样返回，不再新建。
  4. 共享状态：A 调 setLevel(DEBUG) 之后，B 记日志立刻按新阈值过滤——哥俩用的是同一个对象。
  5. 验证：logger1 === logger2 打印 true，铁证：两次拿到的是同一个引用。
  6. 统一查账：程序任何地方调 getHistory()，看到的都是同一本完整日志。

🔍 代码走读

下面是本仓库 TypeScript 实现的骨架（完整版见 ts/singleton/main.ts，有删减）：

ts/singleton/main.ts（简化）
class Logger {
  // 唯一实例：类自己保管，静态私有字段
  private static instance: Logger | undefined;

  private readonly logs: string[] = [];
  private level: LogLevel = LogLevel.INFO;

  // 私有构造函数：外人休想 new Logger()
  private constructor() {}

  // 全局访问点：第一次来才造，之后都用这一个（懒加载）
  static getInstance(): Logger {
    if (Logger.instance === undefined) {
      Logger.instance = new Logger();
    }
    return Logger.instance;
  }

  setLevel(level: LogLevel): void {
    this.level = level;   // 所有"模块"立刻感知新阈值
  }

  log(level: LogLevel, message: string): void {
    if (LOG_LEVEL_RANK[level] < LOG_LEVEL_RANK[this.level]) return; // 低于阈值，丢弃
    this.logs.push(`[${level}] ${message}`);
  }
}

// 两个"模块"拿到的其实是同一个对象
const a = Logger.getInstance();
const b = Logger.getInstance();
a === b;  // true

看懂这段代码，就看懂了整个模式

单例的全部机关就两道锁：构造函数私有（不许自己造）+ 静态字段缓存（造过就不再造）。getInstance() 里那三行 if 是"懒加载"——不用就不造，第一次真用到了才造。

⚖️ 什么时候用，什么时候别用

✅ 适合的场景

  • 全程序确实只能有一份的东西：日志器、配置中心、连接池、线程池
  • 需要一个集中的"总开关"来管理共享状态（比如日志级别）
  • 实例创建昂贵，希望拖到真用的时候再建（懒加载）

❌ 不适合的场景

  • 只是为了"随处都能访问"图方便——那叫全局变量，是坏味道不是模式
  • 单元测试需要替换成假实现——单例把依赖藏死了，测试很痛苦
  • 将来可能要多实例（比如每个用户一份）——现在硬写单例，以后拆得撕心裂肺

⚠️ 容易踩的坑

  • 变相全局变量。什么状态都往单例里塞，最后它长成"什么都知道的上帝对象"，谁都不敢动，一改全崩。
  • 隐藏依赖。类里偷偷 getInstance()，依赖关系从函数签名上完全看不出来——换实现、写测试都无从下手。
  • 并发不安全。本仓库是 TS 单线程演示；在 Java 这类多线程语言里，两个线程同时首次调用可能造出两个实例，得加锁或换更稳的写法。
  • 常驻内存。唯一实例活多久程序活多久，里面囤的东西（比如本例的 logs 数组）只增不减就是慢性内存泄漏。

🔗 和其他模式的关系

  • 观察者模式里的"全局事件总线"几乎总是做成单例——保证大家订阅的是同一份名单。
  • 外观模式的外观对象常常也是单例：整个系统只需要一个对外的门面。
  • 享元模式共享大量细粒度对象，单例可以看作它的极端特例——"只共享一个"。
一 句 话 记 住 它 全公司就一枚章，盖章都得找它。
