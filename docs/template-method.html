行为型

模板方法模式 Template Method

一句话：父类把流程的先后顺序焊死，每一步具体怎么干，留给子类去填空。

← 上一个策略模式 下一个 →访问者模式

🌰 生活里的例子

连锁奶茶店的标准作业流程（SOP）

奶茶总部给每家加盟店发一本操作手册：① 杯子消毒 → ② 加茶底 → ③ 加小料 → ④ 封口出货。这四步的顺序全网点一样，谁也不许乱——先封口再加料，那杯奶茶就废了。

但手册里有两处留着空格："茶底用哪种茶、小料加什么"由各门店自己填。所以同一本手册，做出芒果芋圆也做得出一杯纯茶。还有一条弹性条款："顾客说不要糖，就跳过加糖那步"——不重写整本手册，也能走出不同路径。

对应到模式里：总部手册是父类的模板方法（顺序焊死），"茶底 / 小料"两处空格是抽象方法（子类必须填），"不要糖就跳过"是钩子方法（默认走这条路，想改再改），各家门店就是子类。

😖 没有它会怎样

本仓库的例子是冲泡饮料：茶和咖啡的流程几乎一样——烧水、冲泡、倒杯、加料，只有"泡什么"和"加什么料"不同。最直接的写法：每个类把流程从头抄一遍。

直来直去的写法（问题代码）

Tea 类里写一套 prepare()：烧水 → 浸泡茶叶 → 倒杯 → 加柠檬；Coffee 类里再抄一套：烧水 → 冲泡咖啡粉 → 倒杯 → 加糖奶。其中"烧水""倒杯"两步的代码一字不差地复制了两份。

复制一时爽，维护火葬场：

  • 公共步骤被复制 N 份："烧水"要改成"烧水到 85 度"，得挨个类去改，漏改一个，行为就不一致。
  • 顺序没人把关：哪个类手一抖把"倒杯"写在"冲泡"前面，编译器不报错，喝的时候才知道出事了。
  • 想全局加一步就全城开挖：要求所有饮料出货前"贴标签"，又得往每个类里挨个插代码。

根子上的问题：流程骨架没有单独的家。把骨架提到父类焊死、把会变的步骤挖成空格，重复和失控一起解决。

👥 角色构成（这个模式由几块拼成）

角色大白话职责本仓库示例里是谁
抽象类 + 模板方法 总部手册：把"先干什么后干什么"写死在一个方法里，还负责按顺序指挥每一步。这是全模式唯一的流程入口。 Beverage 抽象类的 prepare()
抽象步骤 手册里的空格："这步我不懂，子类你必须填。"不填，编译都过不去。 brew()、addCondiments()
具体步骤与钩子 公共步骤父类直接实现好；钩子给个默认答案（默认加料），子类想改流程走向时再覆盖。 boilWater()、pourInCup()、customerWantsCondiments()
具体类 填空的人：只把空格补上，流程顺序一点不碰。 Tea、Coffee、BlackCoffee

解耦（把缠在一起的代码拆开，互不认识也能合作）的关键：骨架和实现分了家——顺序只活在父类一份代码里，变与不变各归各位。这背后是"好莱坞原则"：别调用我们，我们会调用你——子类只管交作业，指挥权始终在父类手里。

🗺️ 结构图（谁认识谁、谁调用谁）

Beverage父类 · prepare() 焊死顺序：烧水→冲泡→倒杯→加料
按骨架调用
brew() / addCondiments() 找子类要答案
Tea泡茶叶 · 加柠檬
Coffee泡咖啡粉 · 加糖奶
BlackCoffee只覆盖钩子：不加料

调用方向永远从父类流向子类：骨架调用填空步骤，子类从不反过来指挥流程。外界只认 prepare() 这一个入口。

🔄 运转步骤（跑一遍完整流程）

  1. 点单：new Tea().prepare()——外界只调模板方法这一个入口，不碰任何内部步骤。
  2. 烧水：prepare() 第一步调 boilWater()，父类私有方法，所有饮料共用同一份代码。
  3. 冲泡：调抽象方法 brew()——Tea 填的是"用沸水浸泡茶叶"，Coffee 填的是"用沸水冲泡咖啡粉"，谁实例化就调谁的。
  4. 倒杯：调 pourInCup()，又是公共步骤，一份代码全体复用。
  5. 问一嘴：调钩子 customerWantsCondiments()，默认返回 true；BlackCoffee 把它覆盖成 false。
  6. 加料或跳过：true 就调 addCondiments() 加柠檬 / 糖奶；false 就打印"跳过"——同一套骨架，靠一个钩子走出两条路径。

🔍 代码走读

下面是本仓库 TypeScript 实现的骨架（完整版见 ts/template-method/main.ts，有删减）：

ts/template-method/main.ts（简化）
// 抽象类：骨架写死在父类，外界只认 prepare() 这个入口
abstract class Beverage {
  prepare(): void {                         // 模板方法：流程唯一入口，子类不应重写
    this.boilWater();                       // 公共步骤：父类直接实现
    this.brew();                            // 抽象步骤：留给子类填空
    this.pourInCup();
    if (this.customerWantsCondiments()) {   // 钩子：问一嘴要不要加料
      this.addCondiments();
    } else {
      console.log("（顾客不需要加料，跳过）");
    }
  }

  private boilWater(): void { console.log("1. 把水烧开"); }
  private pourInCup(): void { console.log("3. 把饮料倒入杯中"); }

  protected abstract brew(): void;          // 子类必须实现
  protected abstract addCondiments(): void;

  protected customerWantsCondiments(): boolean {  // 钩子：默认加料
    return true;
  }
}

// 具体类：只填空，不碰顺序
class Tea extends Beverage {
  protected brew(): void { console.log("2. 用沸水浸泡茶叶"); }
  protected addCondiments(): void { console.log("4. 加入柠檬"); }
}

// 只覆盖钩子，就能改变整条流程的走向
class BlackCoffee extends Coffee {
  protected override customerWantsCondiments(): boolean {
    return false;  // 黑咖啡不加糖和奶
  }
}

看懂这段代码，就看懂了整个模式

核心就一件事：父类的 prepare() 按固定顺序调用步骤，遇到抽象方法就去找子类的答案。子类填得再花哨，也动不了"先烧水后倒杯"这条底线——这就是控制权留在父类。

⚖️ 什么时候用，什么时候别用

✅ 适合的场景

  • 几个类的流程步骤一样、只有个别步骤实现不同：冲泡饮料、各种报告导出、各种 HTTP 接口处理
  • 想消灭复制粘贴的重复流程代码，改一处全局生效
  • 要锁死执行顺序，只开放指定的扩展点给子类

❌ 不适合的场景

  • 流程步骤本身经常变——每改一次骨架，全体子类跟着抖三抖
  • 各子类差异大到只有一两步相同——硬凑一个基类，反而更乱
  • 更想运行时灵活换步骤——用组合（策略模式）比继承更松更好拆

⚠️ 容易踩的坑

  • 骨架方法没挡住重写 → 秩序崩塌。TypeScript 没有 final 关键字，本仓库靠注释约定"子类不应重写 prepare()"；哪个子类一意孤行覆盖了它，整个流程保证就没了。
  • 钩子越加越多 → 模板方法变 if 森林。三五个钩子还看得懂，钩子多了没人说得清某次运行走的哪条路。钩子只留给"确实常见的分岔"。
  • 子类实现步骤时偷偷改流程外的状态 → 时序暗坑。比如在构造函数里就触发模板逻辑，父类还没准备好，炸得莫名其妙。
  • 继承层数摞太深 → 改一处抖一片。本仓库 BlackCoffee 到 Coffee 已经两层，再深一层，谁都说不清某个空格最终是谁填的。

🔗 和其他模式的关系

  • 和策略模式都在做"变与不变分离"：模板方法靠继承填空，控制力强；策略靠组合换对象，更灵活。想锁顺序用模板，想随时整套换用策略。
  • 工厂方法模式常作为模板方法里的一步："造出产品"这个空格留给子类填——GoF 里这两个模式本来就是好搭档。
  • 生成器模式也把"组装流程"和"具体步骤"分开，但生成器的流程掌握在指挥者手里可以换，模板方法的骨架焊死在父类身上。
一 句 话 记 住 它 爹定流程，儿子填空：顺序别动，内容随你。
