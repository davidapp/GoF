命令模式 Command

一句话：把"要干的一件事"打包成一个对象——发令的按钮只管按，不认识干活的人；干完还能反悔，把这事原样撤回来。

🌰 生活里的例子

餐厅的点菜单

你坐下点了份"宫保鸡丁"。服务员不认识厨师，也不管这菜怎么炒——她只把菜名写在点菜单上，撕下来夹到后厨窗口。厨师看到单子才开火。菜没上想退？把单子撤回来；想先上凉菜再上热菜？把单子排个队就行。

注意：服务员（发令的人）和厨师（干活的人）从头到尾没说过一句话，全靠一张单子传递。

这个比喻对应模式里的什么：点菜单 = 命令对象（Command，写着"做什么"）；服务员 = 调用者（RemoteControl，只管收单、递单、记账）；厨师 = 接收者（Light，真正干活）；你 = 客户端（决定下什么单）。"退单"就是 undo()，"排队的单子"就是历史栈。

😖 没有它会怎样

本仓库的场景是遥控器控制灯：客厅灯、卧室灯，能开能关，还要能撤销。最直接的写法是按钮的点击处理里直接伸手：

直来直去的写法（问题代码）

按钮被按下时，直接调用具体电器：

livingRoomLight.turnOn() —— 按钮自己动手开灯

这样写眼下能跑，但麻烦在后头：

  • 按钮被迫认识灯的每个方法。哪天这个按钮要改成控制音响？按钮代码整个重写。
  • 想撤销？没门。按钮按完就忘了，压根没有"刚才干了什么"的记录，Ctrl+Z 无从谈起。
  • 想排队、记日志、定时执行？没有"操作"这个实体可以存起来，一切都是空谈。

根子上的问题是"发出指令"和"执行指令"被焊死在一起了。拆开的办法：把指令本身变成一个对象，谁想发就发，发出去还能存。

👥 角色构成（这个模式由几块拼成）

角色大白话职责本仓库示例里是谁
命令 Command 定规矩："每个命令都得会两招——执行 execute、反悔 undo"。 Command 接口
具体命令 一张张具体的"单子"。手里攥着接收者，把活儿转包给它。 LightOnCommand、LightOffCommand（外加空占位的 NoCommand）
接收者 Receiver 真正干活的人：灯知道自己怎么开、怎么关。 Light（客厅灯、卧室灯）
调用者 Invoker 发单子的人。只认识"命令"这个概念，还拿个小本本（历史栈）记下每张发出去的单子。 RemoteControl（遥控器）
客户端 决定哪盏灯配哪条命令，绑到遥控器上。 main() 函数

解耦关键在哪：遥控器只认识 Command 接口，完全不认识灯；命令认识灯，但不认识遥控器。两头各管各的，中间靠"单子"传话——这就是解耦（把缠在一起的代码拆开，互不认识也能合作）。换一种电器？换一张单子就行，遥控器零改动。

🔄 运转步骤（跑一遍完整流程）

  1. 备货：造好接收者——客厅灯 livingRoomLight、卧室灯 bedroomLight，再造一个遥控器。
  2. 绑单：remote.setCommand(new LightOnCommand(livingRoomLight))，把"开客厅灯"这张单子绑到按钮上。
  3. 按下：pressButton() 调 execute()，命令转手调 light.turnOn()——灯亮了；同时这张单子被压进 history 栈。
  4. 继续操作：开卧室灯、关客厅灯……每按一次，栈里就多记一笔。
  5. 撤销：pressUndo() 从栈里弹出最近那张单子，调它的 undo()——"关客厅灯"被倒回成"开客厅灯"。
  6. 再撤：再按一次撤销，弹出更早那张"开卧室灯"，倒回成"关卧室灯"。栈空了就提示"没有可撤销的操作"。

🔍 代码走读

下面是本仓库 TypeScript 实现的骨架（完整版见 ts/command/main.ts，有删减）：

ts/command/main.ts（简化）
// 命令接口：一个动作的抽象——会执行，也得会反悔
interface Command {
  execute(): void;
  undo(): void;
  describe(): string;
}

// 具体命令：手里攥着接收者，把活儿转包给它
class LightOnCommand implements Command {
  constructor(private readonly light: Light) {}

  execute(): void { this.light.turnOn(); }    // 开灯
  undo(): void     { this.light.turnOff(); }  // 反悔 = 关灯
  describe(): string { return "开灯命令"; }
}

// 调用者：遥控器，只认识 Command，完全不认识灯
class RemoteControl {
  private slot: Command = new NoCommand();   // 默认空命令，省得判空
  private readonly history: Command[] = [];  // 操作历史栈

  setCommand(command: Command): void { this.slot = command; }

  pressButton(): void {
    this.slot.execute();          // 执行
    this.history.push(this.slot); // 记账，为撤销做准备
  }

  pressUndo(): void {
    const last = this.history.pop();
    if (last !== undefined) {
      console.log(`撤销上一步：${last.describe()}`);
      last.undo();                // 让单子自己倒回去
    }
  }
}

看懂这段代码，就看懂了整个模式

核心就两个动作：execute 时转包（调接收者）+ undo 时反着转包。遥控器那两行 push / pop 就是撤销功能的全部秘密——把"做过的事"存成对象，反悔时拿出来倒放一遍。

⚖️ 什么时候用，什么时候别用

✅ 适合的场景

  • 需要撤销 / 重做：编辑器的 Ctrl+Z、游戏的读档回退，靠命令对象攒历史栈
  • 需要把操作排队、记日志、定时跑：任务队列、事务日志，装的都是命令对象
  • 发令的组件要和干活的组件彻底解耦：遥控器按钮不绑定具体电器，配置一下就能换

❌ 不适合的场景

  • 操作就一两个、永远不需要撤销——直接调方法，包一层纯属多余
  • 操作没法"反着做"（邮件发出去了没法取消发送）——undo 就是空中楼阁
  • 一堆琐碎小操作都要建命令类——类的数量爆炸，维护成本超过收益

⚠️ 容易踩的坑

  • undo 和 execute 不对称。开灯命令的 undo 里又写成了开灯——每按一次撤销就错一次。写 undo 前先自问：怎么把世界恢复到执行之前？
  • 只有撤销栈、没有重做栈。用户撤销之后想"撤回这次撤销"？没辙。完整体验通常要 undo 栈和 redo 栈成对出现。
  • 命令对象里存错状态。该存的（比如执行前的亮度）没存，撤销就失败；存了一堆用不上的，内存白白被占。存什么、何时存，一开始就要想清楚。
  • 宏命令撤销顺序弄反。批量执行 3 条命令，撤销时得倒着来（后开的灯先关）；正着撤一遍，只会越撤越乱。

🔗 和其他模式的关系

  • 和策略模式长得几乎一模一样（都是"接口 + 一堆实现"），但意图不同：策略是"挑一种做法换着用"，命令是"把动作记下来，好排队、好撤销"。
  • 和备忘录模式都能做撤销：备忘录是"拍快照存状态，撤销时恢复回去"，命令是"记动作，撤销时反着再做一遍"。状态又大又乱用备忘录，动作干净利落用命令。
  • 可以和责任链模式组合：命令对象作为请求沿链传递，由链上的处理者决定接不接、何时执行。
一 句 话 记 住 它 把"要做的事"写成一张单子：发令的只管递单子，干活的照单办事，后悔了就把单子倒着撤一遍。
