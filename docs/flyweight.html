享元模式 Flyweight

一句话：一万个长得一模一样的，只造一个大家轮着用；各自不同的那点差异，自己揣着。

← 上一个外观模式 下一个 →代理模式

🌰 生活里的例子

活字印刷

印一页书，里面出现了 50 个"的"字。刻字工人绝不会刻 50 个一模一样的"的"——他只刻一个铅字，排到哪一行哪个位置，就把这枚铅字拿到哪去用，用完放回字架，下个"的"字继续用它。

注意拆分的艺术：字的形状是死的、大家共用的（刻一次就够）；它在纸上的位置是活的、每个字各不相同（排一个记一个）。

对应到模式里：铅字是"享元"（内在状态：树种、颜色、纹理），字架连同查找规则是"享元工厂"（缓存），每个字在纸上的位置是"外在状态"（坐标）。共享不变的，各存各变的，内存就省下来了。

😖 没有它会怎样

本仓库的例子是一片森林：游戏里要种成千上万棵树。如果每棵树都老老实实造一个"完整对象"：

直来直去的写法（问题代码）

每棵树自带全部数据：

new Tree(1, 1, "橡树", "深绿色", "粗糙树皮纹理图片") × 一万次 ……

这样写眼下能跑，但麻烦在后头：

  • 一万棵橡树，"橡树+深绿+粗糙纹理"这份数据就在内存里重复存了一万份——尤其纹理图片才是内存大户。
  • 真正因树而异的信息其实只有坐标两个数，99% 的内存花在了重复数据上。
  • 对象多到这个量级，创建耗时、垃圾回收压力全跟着遭殃，帧率往下掉。

根子上的问题是：没把"大家一样的"和"各不相同的"拆开，一股脑全塞进了每个对象。

👥 角色构成（这个模式由几块拼成）

角色大白话职责本仓库示例里是谁
享元 Flyweight 那枚铅字：装着内在状态（大家共用的部分），字段全 readonly 谁也改不了。 TreeType（名字 / 颜色 / 纹理）
享元工厂 字架管理员：拿着缓存（Map），来要铅字先查架，有就给，没有才刻一枚。 TreeFactory（静态 cache + getTreeType()）
使用享元的对象 轻得很：只存外在状态（坐标）加一个指向铅字的引用，别的一概不背。 Tree（x、y、type 引用）
客户端 种树的人：报树种要铅字，从不直接 new 享元，一切走工厂。 Forest（plantTree / draw）

解耦（把缠在一起的代码拆开，互不认识也能合作）关键在状态的一拆两半：不变的（长什么样）全局共享一份；变的（站在哪）各存各的。所以 TreeType.draw(x, y) 把坐标当参数临时传进来，而不是存在自己身上——享元身上一个可变字段都没有，共享才安全。

🔄 运转步骤（跑一遍完整流程）

  1. 种树：forest.plantTree(1, 1, "橡树", "深绿色", "粗糙树皮")——Forest 不自己 new 铅字。
  2. 查缓存：TreeFactory 把参数拼成 key"橡树_深绿色_粗糙树皮"，先查 Map。
  3. 首次才造：缓存没有，new 一个 TreeType 存进去；这是这个树种唯一的一次创建。
  4. 之后白拿：后面再种五棵橡树，同一个 key 次次命中，返回的都是同一枚铅字。
  5. 造轻对象：new Tree(x, y, type)——只带坐标和一个引用，轻得像张纸条。
  6. 绘制：tree.draw() 把坐标传给共享的 type.draw(x, y)，同一枚铅字在六个位置各印出一棵树。结果：6 棵树，只有 2 个 TreeType。

🔍 代码走读

下面是本仓库 TypeScript 实现的骨架（完整版见 ts/flyweight/main.ts，有删减）：

ts/flyweight/main.ts（简化）
// 享元：内在状态（树种/颜色/纹理），全 readonly —— 谁也改不了
class TreeType {
  constructor(
    public readonly name: string,
    public readonly color: string,
    public readonly texture: string,
  ) {}
  draw(x: number, y: number): string { // 坐标是外在状态，用时才传进来
    return `在 (${x}, ${y}) 绘制一棵【${this.name}】`;
  }
}

// 享元工厂：按 key 缓存，同一个树种只造一次
class TreeFactory {
  private static readonly cache = new Map<string, TreeType>();

  static getTreeType(name: string, color: string, texture: string): TreeType {
    const key = `${name}_${color}_${texture}`;
    let type = TreeFactory.cache.get(key);
    if (type === undefined) {
      type = new TreeType(name, color, texture); // 首次：真造一个
      TreeFactory.cache.set(key, type);          // 存回字架
    }
    return type; // 之后：直接给缓存里那枚
  }
}

// Tree：只存外在状态（坐标）+ 一个共享引用，轻得很
class Tree {
  constructor(
    private readonly x: number,
    private readonly y: number,
    private readonly type: TreeType, // 指向共享的铅字
  ) {}
  draw(): string { return this.type.draw(this.x, this.y); }
}

// 客户端：种六棵树，铅字只出两枚
forest.plantTree(1, 1, "橡树", "深绿色", "粗糙树皮");
forest.plantTree(3, 8, "白桦", "浅绿色", "光滑树皮");

看懂这段代码，就看懂了整个模式

灵魂就一句：Tree 身上没有树名、没有颜色、没有纹理，只有一个引用。把共享数据从一万个小对象里抽出去，只留一份挂在工厂的 Map 上——省下的就是赚到的。

⚖️ 什么时候用，什么时候别用

✅ 适合的场景

  • 要造海量对象（成千上万），内存真的吃不消——树、粒子、地图格子、字符
  • 对象的大部分状态都重复，能干净地拆成"共享+各变"两块
  • 不在乎对象身份——用不用的是同一个实例，业务看不出来也不在意

❌ 不适合的场景

  • 对象就几百个——省的那点内存，抵不上多写的一层工厂和间接
  • 状态几乎个个不同，根本抽不出可共享的内在状态——缓存命中率归零
  • 业务依赖"这是不是同一个对象"（身份比较）——共享会直接改出 bug

⚠️ 容易踩的坑

  • 内在状态不是不可变的。哪个缺德的在共享的 TreeType 上改了个颜色，全森林的橡树当场集体变色。所以字段必须 readonly，本仓库就是这么做的。
  • 外在状态混进享元。把坐标存进 TreeType，缓存 key 永不重复，每个"树种"都是新的——享元瞬间退化成普通对象，白忙一场。
  • 只算数量不算账。享元自己也是要占内存的：种类多到跟对象数差不多时，共享就没得赚，先测再上。
  • 线程环境下裸奔缓存。多线程同时"首次创建"同一 key，可能造出两份铅字——缓存得是并发安全的。

🔗 和其他模式的关系

  • 和单例模式是亲戚：单例是"全局只此一份"，享元是"每种只此一份"——可以看作把单例推广成了"按种类共享"。
  • 和组合模式常搭伙：树形结构里大量相似的叶子节点，正好用享元共享，一棵 UI 树千千万万个图标就是两回事合一处。
  • 享元工厂本质是个工厂——只是多了张缓存表，造过的不再造。
一 句 话 记 住 它 一样的只造一个大家共用，不一样的自己揣着走。
